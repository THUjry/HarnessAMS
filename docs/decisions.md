# Design Decisions

Design decisions for the `dsh-harnessams` plugin and the HarnessAMS suite, ordered by importance — the top entry is the suite's division of labor. The list is consolidated into ten topic areas, each entry holding that area's atomic decisions as bullets. Every decision states what holds: a replaced decision folds into its successor before the list is renumbered, and the old-numbering map lives in the root repo's stage-1 chronicle appendix. Day-by-day history lives in the root repo's stage chronicle.

## D-001 — Suite division of labor, working environments, and implementation languages

- **SmartAnaSim = pure tool set.** Usable on its own, with no other plugin required and zero references to any other plugin's tools in tool descriptions, file headers or skill text. Spectre is netlist pre-check for hand-written run directories (`spectre_pre_check`, pure JS — see D-005); the `snp_*` family covers S-parameters end to end (`snp_read` is the single entry for `.sNp`/`sp.sp` data files and writes the lossless `%.17g` params CSV that `snp_extract` consumes) and `gen_vsch_*` carries the Virtuoso round-trip command assembly. Sweep execution and routine result parsing are script-face — directly runnable python — because **data processing is not tool-shaped**; the single tool-shaped exception is `post_check`, the on-demand data-integrity diagnostic (collect-style: every point scanned, every rule violation caught and aggregated into one classified report, zero file artifacts) for when sweep results look wrong, empty or incomplete. The parser also takes a standalone `.sp` file directly (`--raw-dir`). Exactly one bundled skill: `smart-spectre`, the spectre configuration reference (a root page plus named companion pages).
- **HarnessAMS = the standardized, process-oriented scan methodology.** `batch_submit` runs sweeps under three schedulers with ONE contract (D-004): a quick launch that returns a non-terminal state — `local` (detached background worker on this host), `ssh` (detached launch on a node reached over ssh) and `lsf` (bsub; the per-environment channels below) — while `batch_poll` is the single monitor face and the only progress card: it waits toward a terminal state, then pulls the fixed light result set (`sweep_progress.json` + `errlog.txt`) — raw psf/sp data stays on the executing host by design and deep analysis runs there — and every frame carries a bounded per-point digest. `gen_sweep_report` renders the analysis report from a model-written spec. `overwrite: true` clears the stale replay markers (`.hams_submitted`/`.hams_ssh_done`) under the flock and tags the fresh ones, so a finished batch re-runs while a replay of the same call still short-circuits. Tool faces: 7 (SmartAnaSim) + 9 (HarnessAMS).
- **Skills split along the same line.** Each package carries the skill for its own surface — `batch-sweep` (generic scan methodology) and `automation` (the workspace task list) in HarnessAMS, `smart-spectre` (spectre configuration) in SmartAnaSim; the dca skills keep their spectre-language content and sky130 examples in place and point at these two for the mechanics.
- **Scope note.** The requirement repo places "run simulation" wholly under SmartAnaSim and lists the HTML report in its function list; this division knowingly diverges and is reconciled at the v0.1.0 release-notes pass.
- **Two working environments, one shared cluster filesystem.** `settings.cluster_env` selects the working environment: `in-cluster` (the DSH host itself is a cluster node) or `out-of-cluster` (the default: the host sits outside the cluster). Both environments assume ONE filesystem shared by all cluster nodes; they differ only in whether the DSH host sits on it. In-cluster, staging writes the shared paths directly and no file ever crosses ssh; out-of-cluster, files cross only the host-to-cluster boundary through dsh-ssh upload/download, never node-to-node.
- **Scheduler semantics follow the environment.** `local` runs on the host itself (in-cluster only; `batch_submit` rejects it out-of-cluster); `ssh` runs the sweep on a node reached over ssh — out-of-cluster that is the ssh node itself (a second hop is the dsh-ssh proxy config's business), in-cluster any other node; `lsf` submits through bsub — locally from the host when in-cluster, through the ssh node when out-of-cluster. The project AGENTS.md block states which environment holds (the yaml `cluster_env` row; the workflow table follows it). Batch submission resolves the configured machine when `machine_id` is omitted — a per-call `machine_id` (or LSF `bsub -m`) is only for spreading across nodes. dsh-ssh aliases never appear in the block: the remote side is stated as paths only (`remote_root`, `remote_scripts_dir`, the self-check group `selfcheck_remote_dir`, and the toolchain pins `remote_python` / `remote_spectre_cmd` — D-006), and the dsh-ssh host list remains the node inventory behind the settings table.
- **JS single implementation inside the plugins.** JS is the single implementation for everything inside the plugins: tool definitions, server routes, analysis/report/trash logic, progress reading (the run-directory ladder in `src/progress_files.js`, shared by the endpoints and the batch tools) and self-check orchestration.
- **Python only in three scenario families.** (1) sweep workers and their result-parsing/diagnostic helpers (e.g. `spectre_sweep_worker.py`, `spectre_psf_parse.py`, `spectre_post_check.py`) that must run where Node cannot be assumed (cluster nodes, or wherever the data sits); (2) S-parameter numeric computing in the numpy/complex-matrix domain — e.g. `snp_extract.py`; (3) per-project user-authored assembly scripts, whose existence as plain project-side scripts is itself the architecture — e.g. `gen_selfcheck_rc.py`. A new Python family needs its own decision entry. Grandfathered exception: the self-check verify twins (`selfcheck_verify.py`/`.mjs`). A port re-baselines its regressions, tolerance-style where floating point differs.

## D-002 — Configuration, project layout, and script staging

- **One config file per project.** Config lives in `<project>/.harnessams/workspace_config.json`: `{ version, workspace: { sim_scripts_dir, trash_dir }, settings: { cluster_env, run_mode, machine_id, remote_root, selfcheck_remote_dir, scheduler, simulator, compute_script_local, compute_script_remote, remote_python, remote_spectre_cmd } }` (the self-check dir key is `selfcheck_`-prefixed — `batch_submit`'s `remote_dir` ARG is the batch output dir, a different thing; legacy configs migrate the old key on read). The workspace section is laid down once with resolved defaults (a fresh project's scripts root is the package install location — the staging bullets below); existing explicit values are never migrated. Env `HARNESSAMS_SIM_SCRIPTS_DIR` overrides. The plotly keys are known but never default-filled: `plotly_url` is declared only after a successful seed-on-open copy and `plotly_asset` is a hand-edit expert override (the plotly chain — D-008). No state migration: legacy state is archived `*_old`, never read; unknown enum values fall back to the defaults. `settings.remote_root` fences every remote `remote_dir`.
- **`harnessams_selfcheck` is the single config write face.** Actions run/status/stop/env/save_agentsmd plus an optional `settings` object written before the action; the UI buttons ride it through `POST /api/tool`. The payload is full or partial: a partial one is merged key by key over the stored settings before validation (the UI keeps sending full drafts).
- **Self-check runs and artifacts.** Runs live under `<project>/.harnessams/selfcheck/<runId>` with project-fenced reads. A clean run's artifacts are deleted at finalize; failed runs keep evidence; the next run cleans history; finalize re-syncs AGENTS.md unconditionally. Check params stay out of the config file (D-003).
- **The AGENTS.md config block: core constraints + yaml + the recommended-workflow table.** The block is tables and bullets only, NO prose paragraphs: (1) core-constraints bullets — ask the user when design constraints are unclear (never guess), execute through the SAS/HA plugin tools and consult the user on failure (no hand-rolled workarounds), `.harnessams/` is plugin storage a model does not read in normal work; (2) the yaml table mirroring workspace_config.json plus measured env facts and the latest self-check verdict — machine aliases are absent, remote facts are paths only (`remote_root`, `remote_scripts_dir`, the tail selfcheck group `selfcheck_remote_dir` + the verdict rows, the toolchain pins `remote_python` / `remote_spectre_cmd`); rows that do not apply (`remote_root`/`remote_scripts_dir` in local mode) are omitted, not null; (3) the recommended-workflow table (`server/selfcheckWorkflow.js` `workflowTable`) — one row per step (Write/Submit/Monitor/Analyze/Report; D-005), each naming the tool and ONLY the parameters the model fills; values the yaml already states are deliberately absent. The scheduler and analyze cells fork on `cluster_env`; the monitor cell carries the polling cadence (10 s -> 20 s -> 40 s backoff, 5 s card refresh, no blind sleeps). The submit cell tells sessions to omit `remote_python` (the project pins resolve it) and the analyze cell names the interpreter through the `remote_python` row, pinned or not. The block is English + ASCII; unknown settings normalize to defaults. Rendered on VALUES builds only (the first-fill template carries constraints + an empty yaml, no table); both save paths (save_agentsmd and the finalize auto-sync) share one change point. When the workflow or tool parameter surface changes, `workflowTable` changes in the same commit: those strings are what agents read in the project AGENTS.md, and a silent drift misleads them.
- **The AGENTS.md workflow table is a purpose-pointer list.** Each row: step, tool, minimal fill hint — parameter semantics and contracts live in the TOOL DESCRIPTIONS (the netlist contract in `spectre_pre_check`'s, the scheduler matrix / lsf_node / overwrite / no_pre_check in `batch_submit`'s, the poll cadence ladder and the analyze recipe in `batch_poll`'s, the report schema in `gen_sweep_report`'s). The HA tools stay eagerly declared: deferred loading (deferLoading) is explicitly not adopted.
- **The configured `machine_id` renders as an AGENTS.md yaml row** (rendered only when set — local mode omits it like every other inapplicable row): the model sees which ssh alias the project's batches and remote-first analysis use, and "Omit machine_id … they resolve from this config" in the workflow table is literally true. The paths-only remote-side stance is unchanged: alias INVENTORIES and host addresses still never render — the machine card / `ssh_list` stays the inventory, and a per-call `machine_id` argument still selects any other alias.
- **AGENTS.md-first reconciliation.** The AGENTS.md config block is AUTHORITATIVE over workspace_config.json, reconciled at BOTH the write and the read faces (the agent prefers editing the outside file, so a hand-edit must take effect immediately and survive the next values sync instead of being clobbered by it). `server/reconcile.js` is the one implementation: a yaml row that is non-null and differs from the stored value is ADOPTED after per-key string-legality validation (validateSettingValue — the same single authority validateSettings loops over); an invalid row is refused — an agent caller gets `warnings[]` in the tool result while the valid adoptions land, a USER caller (the UI route, `source: 'user'`) gets the whole save blocked with the problem list; a null or absent row never clears a stored value (omission is how the renderer skips inapplicable rows; explicit clears go through the `harnessams_selfcheck` settings argument); rows that only make sense together validate as a set. Only a SYNCED block is reconciled — the first-fill template (empty `synced_at`) is a plugin placeholder whose rows carry pre-write defaults, never a hand-edit; the post-write values sync is what marks a block, and every settings write re-renders it (UI = json = AGENTS.md after every write). The write order inside `runSelfcheckAction`: reconcile, merge the payload (the call's explicit intent wins), write, update the node memory for explicit pin writes, then the global-memory null-supplement, then the sync. The read face: `batch_submit` / `batch_poll` resolve their settings at the session project with the block overlaid (`overlaySettingsAt`) — a legal row wins at read time, an illegal row keeps the stored value and surfaces as a warning riding the tool result.
- **Measured python facts are settings keys:** `local_python_version` / `local_python_path` (loose strings — Windows paths legal, length and control-character gates) and the numpy tri-states `local_python_numpy` / `remote_python_numpy` (`yes` = the interpreter imports numpy natively, `fallback` = it does not but the staged numfallback asset imports, `no` = neither — a python 2 shell where even the pure-stdlib fallback has py3 syntax; null = not measured yet). The local family describes the host's bare `python` — one subprocess probe at the self-check finalize, persisted to the settings AND the global local memory; `local_node_version` / `local_node_path` are NOT settings: dsh runs on node, so they render from process at template establishment and every sync, never probed. The remote tri-state rides the D-006 worker telemetry (the worker probes numpy at startup) and lands with the pins on a green run.
- **Design-folder layout.** One design folder per design. The project root holds only `.harnessams/`, `AGENTS.md`, and the design folders; a design folder (e.g. `<project>/Pi12dB/`) holds its run directories (directly under it), `RawResults/`, `SimResults/`, and `Figs/` plus the report HTML. `gen_sweep_report` derives its OUTPUT root from the spec alone — `spec.project_dir`, or the spec's parent's parent when the spec sits in a `SimResults/` directory (the design folder); the model mirrors the remote batch names under `<design>/RawResults/`.
- **The project anchor is the SESSION, never a path walk-up.** `resolveProjectTool` (an explicit `project` argument validated against the registered workspaces, else the calling session's mapping) is the one seam — `batch_submit`, `batch_poll`, `safe_trash`, and `gen_sweep_report` all take an optional `project` argument, and the self-check's nested callTool invocations pass the owning project explicitly (nested exec does not carry the agent id). `resolveWorkspacePathsAt(projectRoot)` resolves the workspace section against a GIVEN root. `gen_sweep_report`'s CONFIG root (sessions store, plotly source, registration) is the session project; without one there is no registration and the plotly chain runs without a project-copy step.
- **Script staging is package-path-first.** A fresh project's scripts root is the PACKAGE install location (the SmartAnaSim scripts sibling in either layout, `defaultSimScriptsDir`) recorded in the workspace config at creation; `initProjectStorage` stages NOTHING and flips nothing (it still lays the config down when the FILE is missing — the session-write asymmetry heal — and the AGENTS.md template while fresh). Every consumer (batch uploads, the local worker spawn, the self-check parser/golden paths, the numfallback probe) resolves through the configured root and reads the package tree directly; a missing worker still fails loud with the sim_scripts_dir guidance. A local `.harnessams/scripts` copy exists only where a config EXPLICITLY points at one — a legacy flipped project or a hand-set root — and is healed lazily at self-check start (`healProjectScriptsAt`): copy-if-missing from the PACKAGE tree (the configured root is the destination, so it cannot be its own source), never clobbering a user-edited file. The numfallback probe anchors at `<resolved scripts root>/../assets` (the package's own bucket for packaged roots). The `<project>/script/` folder does not exist as a convention: the self-check's RC fixture generator (`gen_selfcheck_rc.py`) runs straight from the plugin package's install location (`server/scriptStage.js` `genSelfcheckRcPath()`, `import.meta.dirname`-relative so the dev checkout and an npm-installed bundle resolve identically), cwd = the project root; projects never grow a `script/` tree and models are never pointed at one.
- **Batch-side staging facts.** `batch_submit` uploads the scripts tree plus the sibling assets bucket (`pluginAssets`) on every sync, and `machine_id`/`remote_root` omitted from a call resolve from the project settings.

## D-003 — Sessions, subagents, and stores

- **Every session is a work unit; fork copies are branch-point-independent.** The task concept is retired: there is no task creation/deletion surface. The sidebar strip is exactly project overview + this session (Dashboard + Checks sub-views).
- **The per-session store is `<workspace>/.harnessams/sessions.json`, versionless.** `{ display, reports[], dashboard_selected, check_params?, report_figs?, max_points_per_scan? }` per session — written by single-session merge writes with 200-entry pruning; new sessions start empty. The store carries NO version key and no generation gate: cross-version compatibility is per-field validation. The READ path (`readSessionConfigs`) is lenient — invalid leaves are skipped WITH warnings (a single bad report entry, a stale-shape `check_params`, an invalid `report_figs`/`max_points_per_scan` value, a bad session key or non-object entry), unknown fields ride through reads and writes untouched (a future-format field never disappears by being read), a missing file stays silent (first-run normal), and anything unparsable reads as empty with a warning. Skipped entries self-heal off disk on the next write (the write re-bases on the lenient read view — the warning has already surfaced). The WRITE path keeps the strict {error} contract: a known-field violation rejects the write (the D-009 PUT 400 face). The read returns `{ sessions, warnings }`; the warnings ride `GET /api/session-config` for free and render in the sidebar as one warn line at the top of the session branch (tr summary + ClampText detail; the detail strings are server-side English).
- **`report_figs` is the session's own option:** the `gen_sweep_report` PNG export gate, switched in the session panel above the dashboard and stored on the session entry only while on (strictly boolean; the UI is its only write face). It is not a project setting.
- **Session identity and the check-param chain.** `exec.agent.id` is the SessionId, and `DSH_SESSION_ID` is a shell-env built-in; tools thread it through runPython's env-merge so per-session check params resolve in every worker. Check-param chain: built-ins <- project `check_params.json` <- session table.
- **Fork detection.** rc forks carry no parentSession; the only durable signal is the inherited end-seed marker in the child's zstd session log (`server/forkdetect.js`). A fork copy takes the currently-last-active session's current snapshot — deliberately independent of the branch point — and is served only while the asking session has no entry. Subagents are their own sessions.
- **Subagent identity is the topmost user-visible session.** DSH never accounts a delegated subagent session into any workspace, so a session-keyed operation resolves through `effectiveSessionId(ctx, agent)` (shared `src/subagent.js`): the agent's own id when it is not a subagent, else the FIRST non-subagent ancestor reachable over live `ctx.agents` headers (ordinary forks carry no header origin, so a branch breaks the lineage); a broken chain falls back to the raw id (anchoring then fails with the standard not-accounted error, lookups fail open). The eight HA tools (batch_submit / batch_poll / gen_sweep_report / register_report / safe_trash / harnessams_selfcheck / config_automation / run_automation), the nested `spectre_pre_check` session_id passthrough, and the SAS session faces (`spectre_pre_check`'s session layer, the `DSH_SESSION_ID` worker overlay) all anchor on the effective id. `sessions.json` stays keyed by USER-VISIBLE sessions only: a delegation-run report registers into the user session's entry; a subagent whose lineage did not resolve degrades to no session identity (the report still renders, registration is skipped with a reason) and never writes a child-id entry.
- **Per-session activation state (guide gates) inherits through seeded links:** `inheritsSessionState(ctx, agent, probe)` — a generic predicate/Set probe, snp's `snpActivated` being the first consumer: the walk continues only while every child link is `isSeeded === true` (the inherited history prefix is what carried the state's source fact), a non-seeded subagent earns the state itself, and the state stays registered on the agent that actually read it (never propagated upward or sideways). The policy module is shared VERBATIM between the two plugin repos at `src/subagent.js`: the SmartAnaSim copy is the source of truth (SAS never imports HA; HA already consumes SAS assets), the HarnessAMS copy is a byte-identical mirror, and a dev-layout soft test on each side fails when the two copies drift. Both plugins inject `agents` for the header walk.
- **`register_report` is the standalone registration tool:** it attaches ANY existing local HTML file (not only `gen_sweep_report` output — hand-written or third-party pages included) into the CALLING session's dashboard. Identity and every missing value come from the caller — the entry key (a delegated subagent resolves to its topmost user-visible ancestor, this entry's identity walk), the store location (the calling session's project, or an explicit `project` argument), and the entry's id / name (basename default, overridable) / added_at; there is deliberately NO session_id override (the store stays keyed by user-visible sessions). Failures throw — unlike `gen_sweep_report` there is no on-disk artifact to salvage: the path must exist and be a regular `.html`/`.htm` file; registering is idempotent by absolute path; 32 reports per session. Files not produced by `gen_sweep_report` get no plotly routing — their script tags load exactly what they name. `gen_sweep_report` auto-registration is parameterized: `register` (default true) keeps the session-anchored behavior; `register: false` renders without touching sessions.json, the model attaching the file later via `register_report` from whichever session context it wants. Both tools share the caller anchor and the single-session merge write (`registerReportIntoSession`), and both surface the store's read warnings as `store_warnings` in their results. The identity walk STAYS in `gen_sweep_report`: `register: false` only removes the registration consumer — the config root (plotly chain, D-008) and the `report_figs` PNG gate still resolve by the calling session, so dropping the walk would degrade delegation-run reports.
- **The plugin-global store backs facts that outlive any project:** `HARNESSAMS_GLOBAL_STORE` -> `(DSH_HOME || ~/.dsh)/harnessams.json`. Reads fail open (missing or corrupt = defaults), writes are read-modify-write and atomic. `nodes` — the per-node toolchain memory, keyed by the dsh-ssh machine alias (an in-cluster LSF run with no machine keys by the hostname its telemetry reports). An entry holds the machine's CURRENT pin pair plus host and updatedAt: a green self-check writes it (auto-pin, D-006), an explicit pin write syncs it, an explicit null clears the key and both-null removes the entry — so a prefill (project init, self-check start, save_agentsmd) only ever fills pins the node truly runs. A fresh project on a known machine starts pinned; the heal never overrides an explicit pin. The plugin-global memories fill NULL fields only, never overriding a value the project already holds (the heal covers the toolchain pins plus `remote_python_numpy` from the node entry, machine-scoped, and the `local_python_*` family from the host-scoped `local` section, no machine needed); a remembered null or cleared key never refills — only a later green run re-measures. The settings-payload path runs the supplement AFTER the node-memory write, so an explicit null clear (which clears the memory too) still sticks. `display.selfcheck_fresh_min` (default 30) — the freshness window for the settings-table status restore: when the in-browser run state is gone (page reload, project switch), the panel reads the AGENTS.md managed block (`parseFacts`) — a `last_selfcheck_finished_at` within the window keeps its per-column check marks, past the window the cells flag "not self-checked for > N min", and a null overall keeps the plain dash. The window's write face is the console display settings (`PUT /api/global-config`); `/api/info` publishes it and `/api/project` carries the facts.

## D-004 — The scan flow: skills and templates, the submit contract, monitoring, progress, and limits

- **Bundled skills ride the official host registry:** `ctx.skills.register` per packaged `skills/<name>/SKILL.md` — name/description catalog lines only, bodies load on demand through the host `skill` tool; `resourceBase` = the skill directory; registration is fail-open; `inject` carries `skills`.
- **`template*.scs` family:** the file uploads under its own name and `sweep_config.netlist_template` must match it exactly (a mismatch, an undeclared or a declared-but-missing template fails at submit).
- **Sim naming and batch data layout, same names on both sides.** `Sim<N>_<YYYYMMDD>_batch<M>` — same index with batch+1 on the same day, otherwise index+1 batch 1. `batch_submit.remote_dir` is optional: the next free name under `<remote_root>/RawResults` is picked automatically. The progress layer recognizes `<project>/Sim*/` and `sweep/Sim*/` beside legacy `sweep/RoundN/top`. Batch runs are auto-named `<remote_root>/RawResults/Sim*`, raw local data lands in `<project>/RawResults/`, compact results go to `<project>/SimResults/` via `ssh_download`.
- **dca method:** the shunt-arm total comes from ideal formulas; switch Ron is a direct input (1/3..1/5 of the arm total); ZTC is retired; ideal R/C with real sky130 switches; simulation is authoritative over analytic predictions.
- **The dca skill pair.** `dca-cell-design/` holds unit-cell design (calculators, sky130 example set) — its SKILL.md method text carries no concrete frequency limits or device values; `dca-cascade-analysis` holds cascade analysis plus the absorbed generator: asymmetry removed, ideal RC + switch l/w/nf vocabulary, `--run-dir` mode where NN is the binary control word and the width is the max index's `bit_length`. The sky130 example set splits in two: `sky130proc/` (the runnable process kit — templates with the bare `sp` analysis name, the transcribed switch model per PUBLISH's no-PDK-models carve-out, lvt switch FOM data, plain-nfet Ron/Coff characterization csv) and the verified example layer (`Example.md` + `ST1/T4/Pi8/` per-design `design.json` + two-state raw `sp_ref.sp`/`sp_att.sp`, renamed only); the 4-bit cascade example comes from real sky130 simulations (16 control words) and is carried as cell netlists + results + report only. Skills-tree scrub rules: no asymmetric vocabulary, no dates (two TMTT citations excepted), no machine paths, accounts or IPs (pre-commit hook enforced). The cascade report keeps its own `Analysis/` + CDN-plotly convention, separate from `gen_sweep_report`'s layout.
- **One submit contract across the three schedulers: a quick launch plus poll.** Every scheduler behaves IDENTICALLY toward the session: `batch_submit` is a quick launch — stage the run directory and scripts tree, start the worker, verify startup, record `.batch_job.json`, return a non-terminal state (`running` / `submitted` / `queued`; `completed` only when a done-marker replay short-circuits). All monitoring and light-result retrieval go through `batch_poll` — the single monitor face. Only the launch internals differ: `local` spawns a detached process on this host (in-cluster only), `lsf` uses `bsub` and verifies with `bjobs` plus the started marker, `ssh` launches the guarded worker DETACHED on the target node over ssh.
- **The `ssh` launch is detached.** `nohup sh -c <guarded block> > ssh_worker.log 2>&1 < /dev/null &` where the guarded block is the full command chain (flock + replay check + worker + done marker) — it survives the exec channel closing. The foreground part only cds, runs the pre-lock replay check, launches, and waits a bounded ~20 s for the worker's own `.worker_started` marker; the exec budget is launch-scale (60 s). There is no per-run ssh wall-clock cap: the worker's own global budget is the only run deadline. The launch maps to state `running` (marker seen), `submitted` plus a confirm-by-poll warning (not seen), or `completed` (done-marker replay); the worker's stdout/stderr land in `ssh_worker.log` in the run dir instead of the result's output field. Re-submitting an in-flight or finished dir stays idempotent (flock queues a replay; the done marker short-circuits it).
- **Remote-first analysis is the default recipe:** the put/exec/get triple over dsh-ssh (upload the parser scripts or a self-written analyzer, exec with the cluster's python, download the compact JSON); the batch-sweep skill documents it as the default.
- **Live progress cards: instant first frame + the remote poll endpoint.** A carded call shows content the moment it is invoked (zero-ssh first frame); a batch finishing between polls still shows both frames. `readRunProgress` ladder: progress -> `.worker_started` -> job (`.batch_job.json`) -> config. A submitted-but-unmirrored run dir answers an instant 0/N frame. `GET /api/progress-remote`: same session fence; machine/dir/job resolved server-side from the job file; the batch poll command runs through execRemote (10 s); failures answer `200 {unreachable}` so the card keeps its last frame; a 4 s TTL single-flight per runDir bounds ssh pressure. `batch_poll` carries `wait_sec` (default 0 = snapshot; re-poll ~10 s until terminal or <=600 s, last payload wins) — the blocking call is the live-card window. The client card fetches the remote source at the 5 s wait-policy cadence plus the local ladder on every tick. Presentation: the message-flow card folds with its completed turn — host display policy (desktop default folds completed turns into the "tools called" summary; the card stays mounted but is skipped from painting through hidden-until-found), pixel-verified as never drawn there. There is no plugin-side workaround; user-side visibility for history review is the host transcript-view settings (step display `detailed`, collapse timing `next-input` — direct CLI runs are fast, so the in-flight window is tiny either way), documented in the root repo's UI display spec. The data layer of this entry is unaffected. Custom workers must accept `--work-dir` and write progress atomically WITH a trailing newline.
- **Session-level Max points per scan, enforced at batch_submit.** A session carries a `max_points_per_scan` field (positive integer; written from the HarnessAMS session panel beside the Report-figures toggle; absent = the built-in default 100). It rides the session store (D-003) and the same rebased persist channel (D-009) as `report_figs`. `batch_submit` reads the run directory's `sweep_config.json`, computes the total point count (cross-product = product of the list lengths, zip = the first list's length), resolves the calling session's field through `exec.agent.id` / the session store (fail-open to the default when the session, the store or the config is unreadable), and REJECTS an oversized scan before anything is staged or uploaded. The reject is the model-facing split rule: an oversized grid becomes multiple Sim batches (auto naming), not one mega-run. Submit-time post-check semantics: PEND right after bsub is the expected state — the result reports `state: "queued"` with no warning; RUN without the `.worker_started` marker, a job already EXIT, or an unreadable check produce warnings with wording that says what to do (poll), never "verification failed".
- **The abort contract: every tool honors the session stop; launched jobs are deliberate orphans.** A tool call settles at once when the session stop fires: every HA channel primitive carries the calling tool's `exec.signal` — `execRemote` / `uploadFile` / `downloadFile` pass it into the nested `ctx.tools.execute` batch input (dsh-ssh's `ssh_exec` forwards it into stream KILL + channel close) AND race the batch in `callTool`, because the host never abandons a started tool body ("cancellation never abandons the body": an aborted batch drains to body quiescence, and dsh-ssh sftp has no abort path at all). `execLocal` rides the host shell spec's `signal` (ctx.shell kills the process). The SAS python spawns (`runPython`) pass it into `execFile`'s `options.signal`. The self-check's direct channel calls ride its own cancel controller signal, so the self-check stop cancels in-flight remote execs instead of waiting out their budgets. An ALREADY LAUNCHED job is deliberately left alone — local spawn, nohup'd ssh block and bsub jobs alike (markers + flock make re-runs idempotent; a killed local wait must not require waiting for a remote transfer to unwind). The corollary: an aborted call means the remote/local state is UNCERTAIN, and because the host's `toolAbortedResult` rewrites any aborted call's result to a bare "Error: tool call aborted" (all tool output discarded), the re-verify guidance lives in the TOOL DESCRIPTIONS: check `sweep_progress.json` / `.worker_started` / `.hams_ssh_done` via ssh_exec (or batch_poll once a job file exists) before drawing conclusions or re-submitting. `batch_poll`'s missing-job-record error states the uncertainty explicitly rather than implying "run batch_submit first". Instant tools carry no abort surface (they cannot hold a session): `spectre_pre_check`, `snp_guide`, the `gen_vsch_*` pair, `gen_sweep_report`, `safe_trash`. The stop-button guarantee is about tools that block.

## D-005 — Hand-written run directories; `spectre_pre_check` is the netlist gate inside `batch_submit`

- The recommended workflow's first step is Write: the model hand-authors `template*.scs` + `sweep_config.json` following the dca-cell-design / smart-spectre template contract. `@@P@@` placeholders live on the `parameters` and `include` statements (the include path or `section=` value may sweep — dspf extracts, corner sections; the sole other exemption: `@@temperature@@` on a simulatorOptions line); the circuit references parameters by name. An UNDECLARED `@@temperature@@` is a warning, never an error: the sweep worker substitutes the default 27 degC (recorded in `point_meta.defaulted_params`), so a missing temperature entry never aborts a simulation. Netlist numbers are plain decimals or SI-suffixed literals — scientific notation is banned anywhere on a code line — and ideal R/C/L value positions accept a literal or a bare parameter name ONLY (the shipped idiom: `c=cpf` with suffixed sweep values like `"56f"`). `r/c/l = 0` is the legal degenerate element (short / open). Scripted assembly via a project gen script is an optional legacy path, run directly with the project root as cwd.
- `spectre_pre_check` (SmartAnaSim, pure JS — no python on the check path, so the submit side needs no local python) validates a run directory: language format (incl. the no-scientific-notation rule and the template size gates — warn above 10 KB, reject above 100 KB), sweep-parameter presence, the value gates resolved through the check-param chain (D-003; expressions at R/C/L value positions are rejected, zero values are legal degenerates), and the name gates (reserved-word collisions from the merged official tables are errors on instance/subckt/model/net/parameter name slots — in/out-style net-legal keywords carved out, reserved parameters must-not-declare; names must be C identifiers with integer and bang forms allowed on net names only, the backslash escape banned). The chain's table is `{ rcl, mult, nf_warn, unit_check }`; the `mult` table gates multiplier parameters (`nf` positive integers 1..128, warning at or above the optional `nf_warn` threshold — default 50; `m` rejected by default, released per-line by a `// m-release` comment, then positive integers 1..1000). Session entries that predate the mult table are dropped entry-level on read — new sessions are the bar. The tool's description is functional only — it never prescribes a pre-submit validation call, because the submit-side gate below already runs the same check (a pre-run is a re-run).
- `batch_submit` calls the tool automatically before anything is staged, passing the calling session's id explicitly (a nested tool call's exec identity does not reliably flow); findings fail the submit with the error list, `no_pre_check: true` is the explicit waiver (for reviewed failures only), and a missing tool degrades fail-open to a warning. The self-check's preparation runs the package's `gen_selfcheck_rc.py` directly from its install location and every submission passes through the same gate.

## D-006 — Remote channel and cluster toolchain: absolute-path pins, the second-hop policy, the ssh progress gate

- **The cluster toolchain runs by absolute-path pins: measure, pin, remember.** Every executable the batch channel launches on the cluster side runs by an absolute path held in the project settings. `settings.remote_python` is the interpreter that runs the worker — on every scheduler, `local` included, and under the self-check's remote parse/verify as well. `settings.remote_spectre_cmd` is the spectre executable, passed as `--spectre-cmd` to the bundled worker `spectre/spectre_sweep_worker.py` unless `worker_args` names one (a custom worker keeps its own argument contract). `null` = not yet measured: the bare defaults (`python3`, `spectre` on PATH), exactly what the self-check verified — never bare `python`.
- **Pinning is MEASUREMENT-driven and automatic in the common case:** the bundled worker records what the job really ran under (`sys.executable`, the resolved spectre, the hostname) into `sweep_progress.json`; a GREEN self-check harvests that telemetry, writes the two pins, and remembers them per node in the plugin-global store (D-003), so the AGENTS.md yaml never leaves a run with null pins. Without telemetry (an older worker, `simulator=none`) nothing is written — a path is never guessed.
- **Precedence for the interpreter:** a per-call `remote_python` > the settings pin > the bare default. A per-call value must be an absolute path as well: bare names are refused, because a bare name resolves to whatever the shell startup chain left first on PATH. Sessions omit the argument and read the yaml rows (D-002).
- **A pin is an absolute POSIX path to the executable FILE:** ASCII, no whitespace or shell characters, no `..`, at most 400 characters. One normalizer (`server/settings.js`) guards every face — settings file, tool argument — and an invalid stored value reads as unpinned. The pins are not a settings-table row: the `harnessams_selfcheck` `settings` argument is their explicit write face (the override/clear path — an explicit null clears the node memory with it, so it sticks until a later green run re-measures) and the AGENTS.md yaml is where they are kept.
- **The `cluster-setup` skill is the verification and override face when the automation cannot decide:** harvest (read the login startup chain — `/etc/profile.d`, `~/.bash_profile`, `~/.bashrc` and whatever they source — for the module, PATH and alias lines behind each key command; read-only, the files are the user's), verify (`ssh_exec` probes: what a non-interactive command resolves versus what a login shell does, existence, Python >= 3.7), pin (write through `harnessams_selfcheck` and let the self-check run under exactly those paths). Never guess a path; when candidates disagree, the user chooses — the recommendation put to them is the cluster's own interpreter over a tool-vendored one (a python vendored inside an EDA install leaves with that tool). A shell alias binds a command for the human's interactive shell only — a lead to harvest, never a path a job relies on — and aliases are never removed from the user's files: the work converges on absolute paths on the plugin side.
- **Second-hop (ProxyJump) policy: warn and run direct; a missing alias still fails up front.** `listMachines` keeps ssh_list's per-host `proxyJump` array (the field is schema-required there; empty means a direct connection). When a submit's dsh-ssh target resolves to an entry with an EMPTY jump chain and the channel crosses ssh (scheduler=ssh, or any scheduler out-of-cluster), the submit result carries a warning: the entry has no ProxyJump (second hop) in dsh-ssh, the run is DIRECT, and the fix is the jump chain in the dsh-ssh panel if the host is not directly reachable. A missing jump NEVER blocks the submit. An alias entirely absent from the dsh-ssh registry remains the hard up-front error (resolveMachine, unchanged).
- **The self-check's ssh chain gates on the worker's first progress marker, then polls to a terminal state.** `pollStep` for scheduler=ssh waits for `sweep_progress.json` (or the `.hams_ssh_done` replay marker) BEFORE polling: a 2 s direct probe loop (the user-approved ssh_exec bypass — `runChannel.exec` out-of-cluster, a local stat in-cluster on the shared filesystem), a live "waiting for worker start" status on the step row, a channel-failure abort after 3 consecutive probe errors (no exit code / timed out — exit 1 is "not present yet", never a failure), and the poll budget as the wait ceiling. Once the marker exists, the poll loop runs the ssh chain to a TERMINAL state exactly like lsf. LSF chains skip the gate: bjobs' PEND state is exactly the information a file gate would hide.

## D-007 — Safety, approval, and the browse-only remote root

- **Browse-only remote root.** `remote_root` is set only through the dsh-ssh browse picker — no free-typed row. No saved root -> bootstrap at the machine's `$HOME`; a plain-listing fallback keeps symlinked directories visible. The settings table marks each out-of-sync row (draft vs settings) and follows external writes with a 1 s poll, so fresh sessions never paint red.
- **Self-check stop.** `harnessams_selfcheck` action `stop` flips the cancel flag, aborts in-flight tool calls, bkills LSF jobs best-effort and finalizes `cancelled` with evidence kept — it never enters `last_selfcheck_*`. Self-check submit-step details are failure-first (stale job records demote to annotations); poll steps stream live counts into their step row.
- **Execution-safety guidance lives in the system prompt:** `ctx.systemPrompt.section('harnessams:remote-wait-policy', order 5500)` — safety core only (ask-first on a broken chain, no improvised fallbacks, dsh-ssh tools only, never raw shell ssh); operational cadence (poll intervals, backoff steps, card refresh) lives in the project AGENTS.md workflow table and the batch-sweep skill. Static English, KV-stable. `inject` must declare `systemPrompt` (cordis throws on undeclared ctx access; optional chaining cannot save it).
- **remoteExecGate: a tiered gate for model-initiated remote command execution.** A `ctx.on('tools/pre-execute')` listener gated by the plugin config `remoteExecGate`, in three tiers: `off` (default), `whitelist` (recommended: fixed argument-free allow-listed commands anchored to the whole command string, zero write capability; everything else asks; under a `never` approval policy "outside the whitelist = denied"), `ask-all`. Self-calls are exempt in every tier (the plugin's own check/self-check funnel and the transfer tools). Why tiers and not static analysis: in the default DSH deployment the approval axis idles (pre-execute defaults to allow), and a command's effects cannot be bounded statically — lexical gating is sound only for fixed, argument-free commands. A hard lockdown needs no plugin: set the session read-only. The design holds; the implementation design and its remaining work are tracked in the DSHstudy repo's remote-exec rule-blocking design document (section 5).

## D-008 — Reports and viewing: the pure renderer, the plotly chain, hybrid viewing

- **`gen_sweep_report` is a pure report renderer.** Raw-data processing belongs to the model; the tool only draws. Input = a model-written spec JSON `{project_dir?, title?, conclusions?, out?, rounds:[{id, title?, points, curves?, note?}]}` with points/curves inline or `{"$file"}` references (`project_dir` derives when the spec sits in `<project>/SimResults/`; table columns = the union across points). Output: the report at the project root, its data JS in `SimResults/<report base name>/` — one directory per report, named after the HTML file, so reports of one project that share round ids never overwrite each other's data (a distinct report needs a distinct `out` name; the same name overwrites). Chart PNGs in `Figs/` only when the calling session's `report_figs` option is on (D-003; default off — disk; headless jsdom + bundled plotly + `Plotly.toImage(svg)` + resvg rasterization; deps ship prebuilt, export is fail-open). The report registers into the calling session's dashboard.
- **Charts are curve charts only:** one trace per parameter combination (one design point per curve); scalar metrics render in the table and summary cards, never as charts. Cross-highlight keys on trace-order indices (`sp.indices`), never on label matching; a DOM hit-test fallback covers hosts where `plotly_click` never fires. The in-report batch dropdown lists rounds newest-first (natural id order); the sidebar dashboard orders its report list newest-first by `added_at` and embeds reports 1:1 (no in-document padding/zoom injection).
- **Plotly delivery.** The bundled plotly.min.js inside the plugin tarball is the master copy; projects never get one at generation time. A single per-project copy lives at `<project>/.harnessams/assets/plotly.min.js` (the runtime artifact, never committed, refreshed on size change) and is created ONLY on demand — when the report is opened outside the sidebar, the open-outside-sidebar path seeds it right before the OS viewer launches. The report HEAD is a three-step chain: the in-app `/harnessams/assets/plotly.min.js` route to the packaged copy (the DEFAULT src — same-origin wherever the report is served from the DSH web origin, zero per-project copying), the project copy by relative path (in-page fallback), the CDN (last resort). Reports are offline-capable: the route where the page comes from the web origin, the project copy where it is opened as a local file, the CDN elsewhere. Generation SEEDS NOTHING. `workspace.plotly_url` names the report's project-copy location (the declared value is `.harnessams/assets/plotly.min.js`); the key is NOT default-materialized: the config carries no plotly fields until the seed-on-open copy succeeds — the open-local route calls `declarePlotlyUrl` when `seedProjectPlotly` reports the copy present, which adds the `plotly_url` declaration surgically on the raw JSON (unknown keys and the settings section round-trip verbatim; a present custom or http(s) value is never touched). `plotly_asset` is a hand-edit expert seed-source override only (a present value survives every rewrite; writing the package location by default would pin a stale install as the refresh source). An http(s) `plotly_url` is an expert override used verbatim as the single src (no local file — PNG export skips with its visible reason); a custom local `plotly_url` keeps the direct relative reference (no route step, never seeded, never declared). The PNG exporter falls back to the packaged copy while no project copy exists yet. Scope: delivery only — source selection is the workspace `plotly_asset` field falling back to the packaged copy.
- **Report viewing is hybrid: the embedded iframe viewer plus the system-default open.** Viewing a local report has two coexisting faces: the Dashboard embeds the report in an iframe through the `/dash/<sessionId>/<reportId>/…` serving route (with the hard-reload button and the `/api/report-stat` mtime/size reload poll), and the Open button launches the file with the OS default application via `POST /api/open-local` (`sessionId` + absolute `path`). The embedded view renders offline through the report HEAD's same-origin route step; the external open renders as a file:// document whose relative `SimResults` references resolve offline.
- **The open-local route validates the path** (absolute, existing regular file, VIEWABLE extension whitelist, no `"` / `%` / control characters that could break the quoting) and runs the platform opener (`cmd /c start` / `open` / `xdg-open`) as a DIRECT `node:child_process` spawn with an argument vector — the same local-launch pattern as the python probes and the local batch worker. `ctx.shell` is NOT used for the launch: its workspace-write sandbox is unusable on hosts whose workspace contains `%TEMP%` (the Windows ACL restricted-token runner refuses to start, so every `execLocal` call fails; an instance whose workspace is the user's home directory hits this). `ctx.shell` stays reserved for in-cluster shell command strings (bsub). Report documents opened externally additionally seed the project plotly copy right before the launch and, when the copy is present afterwards, declare `plotly_url` in the workspace config (both fail-open — a seed or declare problem never blocks the open); the response carries the `plotly_seed` outcome, and non-report files open without either. The route carries a same-origin guard (`sec-fetch-site` / `origin`): it is the suite's first route that can trigger an OS process, and it stays a view action — never an execution surface, never an executable/script path, never arguments.

## D-009 — UI interaction: layout rules, the rebased write channel, the remote-root browser

- **Width:** every plugin surface fits the window width. The tab's `.hams-body` is the only scroll container (the console page scrolls itself: `.hams-page { height:100%; overflow-y:auto }`); `table-layout: fixed` plus capped select widths; `overflow-wrap: anywhere` on roots, cells and pre.
- **Long text:** read-only text over 8 rendered lines auto-collapses (ClampText with a measured toggle); tables wrap instead.
- **Sidebar default-open:** opens on first sight of a session in an initialized project (untouched-host-layout gate + workspace mapping retry); blank sessions open via the localStorage layout-key poll about 1 s after creation; an explicit user close wins until another session is entered. The open-state probe requires viewport intersection AND non-hidden visibility.
- **Theming:** native selects theme via `color-scheme` + canvas colors; state colors use `light-dark()` pairs.
- **One rebased client write channel for session configs.** Every sidebar write to a session's `sessions.json` entry goes through the REBASED persist channel: GET the latest server entry, apply the mutator to a clone of it, PUT, adopt the server-confirmed entry (`persistConfig` in `src/client.js`). The store's second writer is server-side and behind the sidebar's back (`gen_sweep_report`'s registration in `src/tools/gen_report.js`), so any channel that PUTs a client-held snapshot without re-reading clobbers injected reports. `mutateConfig` (the first-level tab pills) keeps its optimistic local flip for instant UI and delegates the PUT to the same rebased channel; its mutators must be IDEMPOTENT (applied once to the optimistic snapshot, once to the fresh server base — a display flip is the shape to keep). The first-seen tombstone PUT re-checks the server before writing: an entry the second writer created between the hydrate GET and the PUT is adopted as-is instead of being tombstoned over.
- **The remote-root browser carries an age column, a refresh button, and a create side.** `GET /api/remote-browse` lists one level as `entries: [{ name, mtime }]` (mtime = epoch seconds, null when the plain-ls fallback produced the listing): the primary command is `find -L <dir> -maxdepth 1 -mindepth 1 -type d ! -name '.*' -printf '%P\t%T@\n' 2>/dev/null || ls -1p <dir>` — `-L` keeps symlinked directories visible (the D-007 `ls -L` semantics), the dot filter mirrors ls's default hidden-entry behavior, and a stray broken symlink degrades to the fallback listing exactly as before (ages become dashes). The picker renders each entry's age as "{d}d {h}h ago" (both parts always, future mtimes clamped to zero) with the absolute local time on hover. The current-dir row ends in a square icon-only refresh button (a fixed 16px SVG glyph inside `.hams-iconbtn` — equal padding around the fixed-size icon makes a font-size-independent square); it re-fetches the current level and doubles as the retry after an error. `POST /api/remote-browse/mkdir` is the browser's single remote write: one subdirectory under the currently listed directory, the name validated to a single printable-ASCII segment (trimmed, 1..64 chars, no "/", no leading "." — hidden directories are not listed, so creating one would be invisible), a plain `mkdir` without `-p` so an existing name errors visibly, through the dsh-ssh exec funnel with the open-local-style same-origin fence. The create entry point is the browse dialog alone (an inline form prefilled with `new_folder`, client-side rules mirroring the server's `validateDirName`); success refreshes the listing and never auto-enters or auto-selects the new directory. `remote_root` itself stays browse-pick-only (D-007).

## D-010 — Pickers: every picking surface lives in `src/picker.js`

- **Add-report picking is FILE-first through the plugin's own native dialog.** The add action pops a native OS FILE chooser (`POST /api/pick-file`) — the host ships no file-picker service (its directory pickers hardcode FOS_PICKFOLDERS), so the plugin carries its own: win32 spawns the STA PowerShell script shipped as `src/picker.ps1` (the spike-tested contract — one synthetic Alt press makes a background-spawned dialog take the foreground; exit 0 = the chosen absolute path on stdout, exit 2 = cancel, exit 1 = error; a `taskkill /T` tree kill fences the 10-minute deadline) directly through `node:child_process` (never ctx.shell — the D-008 open-local lesson), linux tries zenity then kdialog, other platforms report unsupported. The dialog filter is pinned to `*.html;*.htm` and the route re-checks the extension (400 on a non-html pick): the picked path IS a single html file with its absolute location, so it registers directly.
- **ANY failure silently falls back to the self-made listing** (no desktop on web-SSH remote sessions, spawn failure, timeout, a non-html pick); a cancel is a 200 no-op; no error surfaces for the attempt and NO system affordance lives inside the dialog. The manual path input carries its own client-side `.html`/`.htm` gate (the store write would reject it anyway, D-009, but that round-trip leaves an optimistic row; the gate keeps the dialog open and explains). The host folder chooser (`POST /api/pick-directory`) stays a public route but is not chained into the add flow. The same-origin guard stays (the pick disturbs the host desktop with a modal dialog — shared with open-local). A 10-minute timeout fences a hung dialog (the abort closes the native dialog and rejects; the rejection becomes a 500 value that the client folds into the silent fallback). The plain-object ctx test seam (`harnessPickFileInternals`) follows the openLauncher pattern: a guarded read that survives the real ctx proxy's undeclared-read throws, production always landing on the real spawn.
- **`src/picker.js` owns every picking backend.** `pickDirectory` (the host `directoryPicker` service consumed through `ctx.get('directoryPicker')` — the one cordis channel that reads a service WITHOUT an inject declaration, undefined when not provided; a static inject would leave the plugin PENDING forever in headless compositions), `pickFile` (the dialog above, with injectable spawn internals for the test face), and `browseDir` (the self-made one-level listing — the fallback picker and the in-dialog file picker; a home-dir default and the manual path input are unchanged). All three resolve the same `{ path }` / `{ canceled: true }` / `{ error, code }` shapes; none ever throws. The PICK LIVES ON THE CAPABILITY OBJECT: `capability()` returns `{ kind: 'native', pick(signal) }` (browse returns `{ kind: 'browse', list, createDirectory }`); `service.pick` is undefined — a kind probe answering 'native' while the call face 503s is exactly this trap.

## D-011 — The automation subsystem: task store, shared command library, dual execution channels

- **Two artifacts.** Command files are the flat shared `.harnessams/automation/` library: plain `.txt` files, single-segment printable-ASCII names, content stored verbatim with zero parsing, reusable across tasks (an identical write is idempotent, a differing write overwrites = editing the library, effective on every referencing task's next run; deleting a task never deletes files, orphans are ordinary safe_trash material). The task store is `.harnessams/automation.json` (versionless; lenient read — bad entries, unknown command names or modes are skipped or defaulted with a surfaced warning; unknown fields ride through reads and writes; strict write; the next write self-heals off disk).
- **Identity and faces.** Entry keys are minted at creation: the creating session's id (a delegated subagent resolves to its topmost user-visible session, D-003) + a yymmddhhmmss local stamp, same-second collisions getting an incrementing suffix. `config_automation` is the only write face (add/update/delete + `mode`; the UI's delete rides `POST /api/automation/delete`, both entry-only); `run_automation` is the agent debug run face (its only argument is the key); the DEFAULT trigger is the sidebar list's manual Run button (`POST /api/automation/run`, never through the agent).
- **Stateless execution with a mode-picked channel.** No in-memory registry gates execution: every run re-reads the command files from disk in the task's order and executes them sequentially, the full per-command result returned with the call. `remote` (default): each file is a shell script through the ssh_exec funnel on the project's `machine_id` (120 s per file, a failure never stops the rest, stdout/stderr truncated at 20k characters each). `local`: each non-comment line is one registered-tool call `toolName {json}` through ctx.tools on this host, no ssh wrapper — only host-scope (globally) registered tools are visible to the channel (agent-scope tools such as `pwsh`/`write` are not; dsh-ssh's `ssh_exec` is host-scope and works), a tool declaring a `project` parameter gets the running task's project path injected (a line-provided value wins), and a line fails per line independently — on a thrown error OR a tool value that reports failure (`ok:false`/`success:false`) — with `tool`/`line`/`text` result rows.
- **`local_exec` is the local channel's host-command tool.** One host-side shell command through the official ctx.shell seam, cwd = the task's project, a 1..110 s deadline plus output caps. Automation-internal: a direct model call is rejected by the caller gate (the calling-source check); its `command` field rides the D-012 red lines; automation never writes files — file writes belong to manual or agent action, the execution-side hard intercept being a filed backlog.
- **Run status lives in the plugin process's memory.** Each task's most recent run — status and full result — is held in process memory only: a light `last_run` on `GET /api/automation`, the full payload on `GET /api/automation/result`; never a disk record (a host restart clears it), and `automation.json` never carries run records.
- **Abort.** The caller's signal races every call and rides the batch input: remote = the channel kills best-effort and remote orphans are deliberate (the D-004 stance), the result marked remote-uncertain; local = whether the in-flight call took effect is uncertain, marked explicitly the same way.
- **Oversize warning and seeding.** A command file over 50 lines warns in the config result, the run result and the list — heavy content belongs on the server first, referenced by path (ssh bandwidth); the warning tail points at the bundled `automation` skill. A fresh project with no automation.json gets one local demo task seeded through `POST /api/project-init` (it empties the project trash through safe_trash's `empty` action); a deleted task never resurrects. Post-run behavior is a reserved seam: the result payload is the extension point, today only echoed by the caller.

## D-012 — Always-on safety red lines

- **Three pre-execute denials, no tiers, no escape hatch.** A `ctx.on('tools/pre-execute')` listener is registered unconditionally at plugin load (`src/core/safetyrules.js`, wired from `src/index.js`) and denies: (1) any `bash`/`pwsh`/`local_exec` command carrying a standalone `ssh` token — boundaries are a preceding character outside `[A-Za-z0-9_.-]` and a following whitespace/quote/end, so `dsh-ssh`, `ssh-keygen`, `sshpass`, `ssh_exec`, `x.ssh` never trip, while argument positions, `bash -c "ssh ..."` nestings, pipes, `$(ssh ...)` and newline-led forms all do, deliberately, so denial cannot be routed around by re-nesting (false positives like `grep ssh file` are accepted and the deny reason carries the sanctioned alternative); (2) a `read` whose `file_path` contains "PDK" (case-insensitive substring); (3) an `ssh_download` whose `remotePath` or `localPath` contains "PDK" (alias excluded, field-scoped), and a `local_exec` whose `command` contains "PDK" (the local host shell — the one local surface that could reach PDK content; the automation local channel's task lines cannot carry raw ssh or PDK strings either). Deny reasons are model-visible tool results stating why and what to do instead (the dsh-ssh tools for ssh; include lines from existing simulation logs, or ask the user for PDK). The tiered remoteExecGate (D-007) is a separate, unimplemented design and adds nothing here; the `remote-wait-policy` system-prompt section states the ssh leg as enforced.
