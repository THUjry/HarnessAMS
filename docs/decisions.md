# Design Decisions

Design decisions for the `dsh-harnessams` plugin and the HarnessAMS suite, ordered by importance — the top entry is the suite's division of labor. Each entry states what holds: every entry is accepted, and a replaced decision folds into its successor. IDs are stable and cited by external documents. Day-by-day history lives in the root repo's chronicle.

## D-001 — Suite division of labor: SmartAnaSim is a pure standalone tool set, HarnessAMS owns the managed scan flow

- **SmartAnaSim = pure tool set.** Usable on its own, with no other plugin required and zero references to any other plugin's tools in tool descriptions, file headers or skill text. Spectre is netlist pre-check for hand-written run directories (`spectre_pre_check`, pure JS — see D-020); the `snp_*` family covers S-parameters end to end (`snp_read` is the single entry for `.sNp`/`sp.sp` data files and writes the lossless `%.17g` params CSV that `snp_extract` consumes) and `gen_vsch_*` carries the Virtuoso round-trip command assembly. Sweep execution and routine result parsing are script-face — directly runnable python — because **data processing is not tool-shaped**; the single tool-shaped exception is `post_check`, the on-demand data-integrity diagnostic (collect-style: every point scanned, every rule violation caught and aggregated into one classified report, zero file artifacts) for when sweep results look wrong, empty or incomplete. The parser also takes a standalone `.sp` file directly (`--raw-dir`). Exactly one bundled skill: `smart-spectre`, the spectre configuration reference (a root page plus named companion pages).
- **HarnessAMS = the standardized, process-oriented scan methodology.** `batch_submit` runs sweeps under three schedulers: `local` (detached background worker on this host; submit returns immediately), `ssh` (run on a node reached over ssh, foreground) and `lsf` (bsub; see D-002 for the per-environment channels). `batch_poll` is the single monitor face and the only progress card: it waits toward a terminal state, then pulls the fixed light result set (`sweep_progress.json` + `errlog.txt`) — raw psf/sp data stays on the executing host by design and deep analysis runs there — and every frame carries a bounded per-point digest. `gen_sweep_report` renders the analysis report from a model-written spec. `overwrite: true` clears the stale replay markers (`.hams_submitted`/`.hams_ssh_done`) under the flock and tags the fresh ones, so a finished batch re-runs while a replay of the same call still short-circuits. Tool faces: 7 (SmartAnaSim) + 5 (HarnessAMS).
- **Skills split along the same line.** Each package carries the skill for its own surface — `batch-sweep` (generic scan methodology) in HarnessAMS, `smart-spectre` (spectre configuration) in SmartAnaSim; the dca skills keep their spectre-language content and sky130 examples in place and point at these two for the mechanics.
- **Scope note.** The requirement repo places "run simulation" wholly under SmartAnaSim and lists the HTML report in its function list; this division knowingly diverges and is reconciled at the v0.1.0 release-notes pass.

## D-002 — Two working environments (in-cluster / out-of-cluster); one shared cluster filesystem

- `settings.cluster_env` selects the working environment: `in-cluster` (the DSH host itself is a cluster node) or `out-of-cluster` (the default: the host sits outside the cluster).
- Both environments assume ONE filesystem shared by all cluster nodes; they differ only in whether the DSH host sits on it. In-cluster, staging writes the shared paths directly and no file ever crosses ssh; out-of-cluster, files cross only the host-to-cluster boundary through dsh-ssh upload/download, never node-to-node.
- Scheduler semantics follow the environment: `local` runs on the host itself (in-cluster only; `batch_submit` rejects it out-of-cluster); `ssh` runs the sweep on a node reached over ssh — out-of-cluster that is the ssh node itself (a second hop is the dsh-ssh proxy config's business), in-cluster any other node; `lsf` submits through bsub — locally from the host when in-cluster, through the ssh node when out-of-cluster.
- The project AGENTS.md block states which environment holds (the yaml `cluster_env` row; the workflow table follows it). Batch submission resolves the configured machine when `machine_id` is omitted — a per-call `machine_id` (or LSF `bsub -m`) is only for spreading across nodes. dsh-ssh aliases never appear in the block: the remote side is stated as paths only (`remote_root`, `remote_scripts_dir`, the self-check group `selfcheck_remote_dir`, and the toolchain pins `remote_python` / `remote_spectre_cmd` — D-016), and the dsh-ssh host list remains the node inventory behind the settings table.

## D-003 — JS single implementation inside the plugins; Python only in three scenario families

- JS is the single implementation for everything inside the plugins: tool definitions, server routes, analysis/report/trash logic, progress reading (the run-directory ladder in `src/progress_files.js`, shared by the endpoints and the batch tools) and self-check orchestration.
- Python is confined to three families: (1) sweep workers and their result-parsing/diagnostic helpers (e.g. `spectre_sweep_worker.py`, `spectre_psf_parse.py`, `spectre_post_check.py`) that must run where Node cannot be assumed (cluster nodes, or wherever the data sits); (2) S-parameter numeric computing in the numpy/complex-matrix domain — e.g. `snp_extract.py`; (3) per-project user-authored assembly scripts, whose existence as plain project-side scripts is itself the architecture — e.g. `gen_selfcheck_rc.py`. A new Python family needs its own decision entry.
- Grandfathered exception: the self-check verify twins (`selfcheck_verify.py`/`.mjs`). A port re-baselines its regressions, tolerance-style where floating point differs.

## D-004 — One config file per project; `harnessams_selfcheck` is the single config write face; self-check artifact cleanup

- Config lives in `<project>/.harnessams/workspace_config.json`: `{ version, workspace: { sim_scripts_dir, plotly_asset, trash_dir }, settings: { cluster_env, run_mode, machine_id, remote_root, selfcheck_remote_dir, scheduler, simulator, compute_script_local, compute_script_remote, remote_python, remote_spectre_cmd } }` (the self-check dir key is `selfcheck_`-prefixed — `batch_submit`'s `remote_dir` ARG is the batch output dir, a different thing; legacy configs migrate the old key on read). The workspace section is laid down once with resolved defaults (fresh projects stage a project-local scripts copy at `<project>/.harnessams/scripts` and point `sim_scripts_dir` there — D-015; existing explicit values are never migrated); env `HARNESSAMS_SIM_SCRIPTS_DIR` overrides. No state migration: legacy state is archived `*_old`, never read; unknown enum values fall back to the defaults.
- `settings.remote_root` fences every remote `remote_dir`.
- `harnessams_selfcheck` — actions run/status/stop/env/save_agentsmd plus an optional `settings` object written before the action — is the single config write face; the UI buttons ride it through `POST /api/tool`. The payload is full or partial: a partial one is merged key by key over the stored settings before validation (the UI keeps sending full drafts).
- Self-check runs live under `<project>/.harnessams/selfcheck/<runId>` with project-fenced reads. A clean run's artifacts are deleted at finalize; failed runs keep evidence; the next run cleans history; finalize re-syncs AGENTS.md unconditionally. Check params stay out of the config file (D-005).

## D-005 — Every session is a work unit; fork copies are branch-point-independent

- The task concept is retired: there is no task creation/deletion surface. The sidebar strip is exactly project overview + this session (Dashboard + Checks sub-views).
- Per-session store `<workspace>/.harnessams/sessions.json` v2 — `{ display, reports[], dashboard_selected, check_params?, report_figs? }` per session — written by single-session merge writes with 200-entry pruning. New sessions start empty.
- `report_figs` is the session's own option: the `gen_sweep_report` PNG export gate, switched in the session panel above the dashboard and stored on the session entry only while on (strictly boolean; the UI is its only write face). It is not a project setting.
- Session identity: `exec.agent.id` is the SessionId, and `DSH_SESSION_ID` is a shell-env built-in; tools thread it through runPython's env-merge so per-session check params resolve in every worker. Check-param chain: built-ins ← project `check_params.json` ← session table.
- Fork detection: rc forks carry no parentSession; the only durable signal is the inherited end-seed marker in the child's zstd session log (`server/forkdetect.js`). A fork copy takes the currently-last-active session's current snapshot — deliberately independent of the branch point — and is served only while the asking session has no entry. Subagents are their own sessions.

## D-006 — `gen_sweep_report` is a pure report renderer; RawResults/SimResults/Figs layout; remote-first analysis

- Raw-data processing belongs to the model; the tool only draws. Input = a model-written spec JSON `{project_dir?, title?, conclusions?, out?, rounds:[{id, title?, points, curves?, note?}]}` with points/curves inline or `{"$file"}` references (`project_dir` derives when the spec sits in `<project>/SimResults/`; table columns = the union across points).
- Output: the report at the project root, its data JS in `SimResults/<report base name>/` — one directory per report, named after the HTML file, so reports of one project that share round ids never overwrite each other's data (a distinct report needs a distinct `out` name; the same name overwrites). Chart PNGs in `Figs/` only when the calling session's `report_figs` option is on (D-005; default off — disk; headless jsdom + bundled plotly + `Plotly.toImage(svg)` + resvg rasterization; deps ship prebuilt, export is fail-open). The report registers into the calling session's dashboard.
- Charts are curve charts only: one trace per parameter combination (one design point per curve); scalar metrics render in the table and summary cards, never as charts. Cross-highlight keys on trace-order indices (`sp.indices`), never on label matching; a DOM hit-test fallback covers hosts where `plotly_click` never fires. The in-report batch dropdown lists rounds newest-first (natural id order); the sidebar dashboard orders its report list newest-first by `added_at` and embeds reports 1:1 (no in-document padding/zoom injection).
- Layout, same names on both sides: batch runs are auto-named `<remote_root>/RawResults/Sim*`, raw local data lands in `<project>/RawResults/`, compact results go to `<project>/SimResults/` via `ssh_download`.
- Remote-first analysis = the put/exec/get triple over dsh-ssh (upload the parser scripts or a self-written analyzer, exec with the cluster's python, download the compact JSON); the batch-sweep skill documents it as the default.

## D-007 — Bundled skills; the `template*.scs` family; the Sim run-dir convention; the dca method

- Skills ride the official host registry: `ctx.skills.register` per packaged `skills/<name>/SKILL.md` — name/description catalog lines only, bodies load on demand through the host `skill` tool; `resourceBase` = the skill directory; registration is fail-open; `inject` carries `skills`.
- `template*.scs` family: the file uploads under its own name and `sweep_config.netlist_template` must match it exactly (a mismatch, an undeclared or a declared-but-missing template fails at submit).
- Sim naming: `Sim<N>_<YYYYMMDD>_batch<M>` — same index with batch+1 on the same day, otherwise index+1 batch 1. `batch_submit.remote_dir` is optional: the next free name under `<remote_root>/RawResults` is picked automatically. The progress layer recognizes `<project>/Sim*/` and `sweep/Sim*/` beside legacy `sweep/RoundN/top`.
- dca method: the shunt-arm total comes from ideal formulas; switch Ron is a direct input (1/3..1/5 of the arm total); ZTC is retired; ideal R/C with real sky130 switches; simulation is authoritative over analytic predictions.

## D-008 — Live progress cards: instant first frame + the remote poll endpoint

- A carded call shows content the moment it is invoked (zero-ssh first frame); a batch finishing between polls still shows both frames.
- `readRunProgress` ladder: progress → `.worker_started` → job (`.batch_job.json`) → config. A submitted-but-unmirrored run dir answers an instant 0/N frame.
- `GET /api/progress-remote`: same session fence; machine/dir/job resolved server-side from the job file; the batch poll command runs through execRemote (10 s); failures answer `200 {unreachable}` so the card keeps its last frame; a 4 s TTL single-flight per runDir bounds ssh pressure.
- `batch_poll` carries `wait_sec` (default 0 = snapshot; re-poll ~10 s until terminal or ≤600 s, last payload wins) — the blocking call is the live-card window. The client card fetches the remote source at the 5 s wait-policy cadence plus the local ladder on every tick.
- Presentation: the message-flow card folds with its completed turn — host display policy (desktop default folds completed turns into the "tools called" summary; the card stays mounted but is skipped from painting through hidden-until-found), pixel-verified as never drawn there. There is no plugin-side workaround; user-side visibility for history review is the host transcript-view settings (step display `detailed`, collapse timing `next-input` — direct CLI runs are fast, so the in-flight window is tiny either way), documented in the root repo's UI display spec. The data layer of this entry is unaffected.
- Custom workers must accept `--work-dir` and write progress atomically WITH a trailing newline.

## D-009 — Browse-only remote root; self-check stop; the system-prompt waiting policy

- `remote_root` is set only through the dsh-ssh browse picker — no free-typed row. No saved root → bootstrap at the machine's `$HOME`; a plain-listing fallback keeps symlinked directories visible.
- The settings table marks each out-of-sync row (draft vs settings) and follows external writes with a 1 s poll, so fresh sessions never paint red.
- `harnessams_selfcheck` action `stop` flips the cancel flag, aborts in-flight tool calls, bkills LSF jobs best-effort and finalizes `cancelled` with evidence kept — it never enters `last_selfcheck_*`.
- Self-check submit-step details are failure-first (stale job records demote to annotations); poll steps stream live counts into their step row.
- Execution-safety guidance lives in the system prompt: `ctx.systemPrompt.section('harnessams:remote-wait-policy', order 5500)` — safety core only (ask-first on a broken chain, no improvised fallbacks, dsh-ssh tools only, never raw shell ssh); operational cadence (poll intervals, backoff steps, card refresh) lives in the project AGENTS.md workflow table and the batch-sweep skill. Static English, KV-stable. `inject` must declare `systemPrompt` (cordis throws on undeclared ctx access; optional chaining cannot save it).

## D-010 — The AGENTS.md config block: core constraints + yaml + the recommended-workflow table

- The block is tables and bullets only, NO prose paragraphs: (1) core-constraints bullets — ask the user when design constraints are unclear (never guess), execute through the SAS/HA plugin tools and consult the user on failure (no hand-rolled workarounds), `.harnessams/` is plugin storage a model does not read in normal work; (2) the yaml table mirroring workspace_config.json plus measured env facts and the latest self-check verdict — machine aliases are absent, remote facts are paths only (`remote_root`, `remote_scripts_dir`, the tail selfcheck group `selfcheck_remote_dir` + the verdict rows, the toolchain pins `remote_python` / `remote_spectre_cmd`); rows that do not apply (`remote_root`/`remote_scripts_dir` in local mode) are omitted, not null; (3) the recommended-workflow table (`server/selfcheckWorkflow.js` `workflowTable`) — one row per step (Write/Submit/Monitor/Analyze/Report; D-020), each naming the tool and ONLY the parameters the model fills; values the yaml already states are deliberately absent.
- The scheduler and analyze cells fork on `cluster_env`; the monitor cell carries the polling cadence (10 s -> 20 s -> 40 s backoff, 5 s card refresh, no blind sleeps). The submit cell tells sessions to omit `remote_python` (the project pins resolve it) and the analyze cell names the interpreter through the `remote_python` row, pinned or not.
- The block is English + ASCII; unknown settings normalize to defaults. Rendered on VALUES builds only (the first-fill template carries constraints + an empty yaml, no table); both save paths (save_agentsmd and the finalize auto-sync) share one change point.
- When the workflow or tool parameter surface changes, `workflowTable` changes in the same commit: those strings are what agents read in the project AGENTS.md, and a silent drift misleads them.

## D-011 — dca-design split into dca-cell-design + dca-cascade-analysis; the AsymATT generator absorbed; scrub rules for the skills tree

- `dca-cell-design/` holds unit-cell design (calculators, sky130 example set) — its SKILL.md method text carries no concrete frequency limits or device values; `dca-cascade-analysis` holds cascade analysis plus the absorbed generator: asymmetry removed, ideal RC + switch l/w/nf vocabulary, `--run-dir` mode where NN is the binary control word and the width is the max index's `bit_length`.
- The sky130 example set splits in two: `sky130proc/` (the runnable process kit — templates with the bare `sp` analysis name, the transcribed switch model per PUBLISH's no-PDK-models carve-out, lvt switch FOM data, plain-nfet Ron/Coff characterization csv) and the verified example layer (`Example.md` + `ST1/T4/Pi8/` per-design `design.json` + two-state raw `sp_ref.sp`/`sp_att.sp`, renamed only); the 4-bit cascade example comes from real sky130 simulations (16 control words) and is carried as cell netlists + results + report only.
- Skills-tree scrub rules: no asymmetric vocabulary, no dates (two TMTT citations excepted), no machine paths, accounts or IPs (pre-commit hook enforced).
- The cascade report keeps its own `Analysis/` + CDN-plotly convention, separate from `gen_sweep_report`'s layout.

## D-012 — remoteExecGate: a tiered gate for model-initiated remote command execution

- A `ctx.on('tools/pre-execute')` listener gated by the plugin config `remoteExecGate`, in three tiers: `off` (default), `whitelist` (recommended: fixed argument-free allow-listed commands anchored to the whole command string, zero write capability; everything else asks; under a `never` approval policy "outside the whitelist = denied"), `ask-all`. Self-calls are exempt in every tier (the plugin's own check/self-check funnel and the transfer tools).
- Why tiers and not static analysis: in the default DSH deployment the approval axis idles (pre-execute defaults to allow), and a command's effects cannot be bounded statically — lexical gating is sound only for fixed, argument-free commands. A hard lockdown needs no plugin: set the session read-only.
- Implementation: not built yet — tracked in the root repo `dev/todo/remoteExecGate.md`.

## D-013 — Plotly delivery for generated reports

- One copy per workspace at `<workspace_root>/assets/plotly.min.js`, seeded on demand from an explicit `--plotly` path, an ancestor-probed package copy, or the workspace `plotly_asset` field (refreshed on size change). The copy is a runtime artifact, never committed.
- Reports reference it workspace-relatively, with the in-app `/harnessams/assets/plotly.min.js` fallback when viewed through the dashboard route and the CDN as the last resort (`--plotly-cdn` forces it). Reports are offline-capable by default and render charts only when the workspace tree travels with them.
- Scope: delivery only. Source selection is not decided here; the default source is the workspace `plotly_asset` field (D-004).

## D-014 — UI layout & session-surface rules

- Width: every plugin surface fits the window width. The tab's `.hams-body` is the only scroll container (the console page scrolls itself: `.hams-page { height:100%; overflow-y:auto }`); `table-layout: fixed` plus capped select widths; `overflow-wrap: anywhere` on roots, cells and pre.
- Long text: read-only text over 8 rendered lines auto-collapses (ClampText with a measured toggle); tables wrap instead.
- Sidebar default-open: opens on first sight of a session in an initialized project (untouched-host-layout gate + workspace mapping retry); blank sessions open via the localStorage layout-key poll about 1 s after creation; an explicit user close wins until another session is entered. The open-state probe requires viewport intersection AND non-hidden visibility.
- Theming: native selects theme via `color-scheme` + canvas colors; state colors use `light-dark()` pairs.

## D-015 — One-time project script staging: what the self-check exercises stays usable afterwards

- Every project keeps its own reusable copy of the simulation scripts: `<project>/script/analysis/gen_selfcheck_rc.py` (the RC fixture generator the self-check runs directly — without it the spectre self-check chain cannot prepare its run directories) and `<project>/.harnessams/scripts/` + the sibling `<project>/.harnessams/assets/` (the worker tree and the numfallback bucket; snp_common resolves `assets/` as a sibling of the scripts root, so the local layout and the remote upload layout — `<remote_root>/.harnessams/{scripts,assets}` — share one shape).
- Staging is copy-if-missing per file (user-edited copies are never clobbered, partial trees complete, up-to-date projects no-op). The PRIMARY timing is project initialization — the sidebar opening the project (`POST /api/project-init`, fired once per project per page load); the fresh config write and every self-check start are backstops. Source: `HARNESSAMS_SIM_SCRIPTS_DIR` -> the configured `sim_scripts_dir` (pre-flip) -> the dev-sibling default (`server/scriptStage.js`). A session-config write that created `.harnessams` first no longer suppresses staging: the init hook stages and flips regardless of who created the store.
- `sim_scripts_dir` flips to the project-local copy (`<project>/.harnessams/scripts`) only while the configured value is still the packaged default — a hand-edited explicit value stays (legacy projects keep their contract).
- The self-check's gen step runs against the REAL project root (the staged gen script), never a throwaway run-dir copy — a passing check must not outlive its scripts.
- `batch_submit` uploads the scripts tree plus the sibling assets bucket (`pluginAssets`) on every sync; `machine_id`/`remote_root` omitted from a call resolve from the project settings.

## D-016 — The cluster toolchain as absolute-path pins: measure, pin, remember

- Every executable the batch channel launches on the cluster side runs by an absolute path held in the project settings. `settings.remote_python` is the interpreter that runs the worker — on every scheduler, `local` included, and under the self-check's remote parse/verify as well. `settings.remote_spectre_cmd` is the spectre executable, passed as `--spectre-cmd` to the bundled worker `spectre/spectre_sweep_worker.py` unless `worker_args` names one (a custom worker keeps its own argument contract). `null` = not yet measured: the bare defaults (`python3`, `spectre` on PATH), exactly what the self-check verified — never bare `python`.
- Pinning is MEASUREMENT-driven and automatic in the common case: the bundled worker records what the job really ran under (`sys.executable`, the resolved spectre, the hostname) into `sweep_progress.json`; a GREEN self-check harvests that telemetry, writes the two pins, and remembers them per node in the plugin-global store (D-017), so the AGENTS.md yaml never leaves a run with null pins. Without telemetry (an older worker, `simulator=none`) nothing is written — a path is never guessed.
- Precedence for the interpreter: a per-call `remote_python` > the settings pin > the bare default. A per-call value must be an absolute path as well: bare names are refused, because a bare name resolves to whatever the shell startup chain left first on PATH. Sessions omit the argument and read the yaml rows (D-010).
- A pin is an absolute POSIX path to the executable FILE: ASCII, no whitespace or shell characters, no `..`, at most 400 characters. One normalizer (`server/settings.js`) guards every face — settings file, tool argument — and an invalid stored value reads as unpinned. The pins are not a settings-table row: the `harnessams_selfcheck` `settings` argument is their explicit write face (the override/clear path — an explicit null clears the node memory with it, so it sticks until a later green run re-measures) and the AGENTS.md yaml is where they are kept.
- The `cluster-setup` skill is the verification and override face when the automation cannot decide: harvest (read the login startup chain — `/etc/profile.d`, `~/.bash_profile`, `~/.bashrc` and whatever they source — for the module, PATH and alias lines behind each key command; read-only, the files are the user's), verify (`ssh_exec` probes: what a non-interactive command resolves versus what a login shell does, existence, Python >= 3.7), pin (write through `harnessams_selfcheck` and let the self-check run under exactly those paths). Never guess a path; when candidates disagree, the user chooses — the recommendation put to them is the cluster's own interpreter over a tool-vendored one (a python vendored inside an EDA install leaves with that tool). A shell alias binds a command for the human's interactive shell only — a lead to harvest, never a path a job relies on — and aliases are never removed from the user's files: the work converges on absolute paths on the plugin side.

## D-017 — Plugin-global store: node toolchain memory + the self-check freshness window

- One machine-scope file backs facts that outlive any project: `HARNESSAMS_GLOBAL_STORE` -> `(DSH_HOME || ~/.dsh)/harnessams.json`. Reads fail open (missing or corrupt = defaults), writes are read-modify-write and atomic.
- `nodes` — the per-node toolchain memory, keyed by the dsh-ssh machine alias (an in-cluster LSF run with no machine keys by the hostname its telemetry reports). An entry holds the machine's CURRENT pin pair plus host and updatedAt: a green self-check writes it (auto-pin, D-016), an explicit pin write syncs it, an explicit null clears the key and both-null removes the entry — so a prefill (project init, self-check start, save_agentsmd) only ever fills pins the node truly runs. A fresh project on a known machine starts pinned; the heal never overrides an explicit pin.
- `display.selfcheck_fresh_min` (default 30) — the freshness window for the settings-table status restore: when the in-browser run state is gone (page reload, project switch), the panel reads the AGENTS.md managed block (`parseFacts`) — a `last_selfcheck_finished_at` within the window keeps its per-column check marks, past the window the cells flag "not self-checked for > N min", and a null overall keeps the plain dash. The window's write face is the console display settings (`PUT /api/global-config`); `/api/info` publishes it and `/api/project` carries the facts.

## D-018 — The configured machine_id renders as an AGENTS.md yaml row

- The project AGENTS.md hams-config yaml renders `machine_id` as one row (rendered only when set — local mode omits it like every other inapplicable row): the model sees which ssh alias the project's batches and remote-first analysis use, and "Omit machine_id … they resolve from this config" in the workflow table is literally true. Supersedes the "the dsh-ssh alias never appears in the block" clause of the 2026-11-24 projection ruling; the paths-only remote-side stance is unchanged.
- Alias INVENTORIES and host addresses still never render — the machine card / `ssh_list` stays the inventory, and a per-call `machine_id` argument still selects any other alias.

## D-019 — Session-level Max points per scan, enforced at batch_submit

- A session carries a `max_points_per_scan` field (positive integer; written from the HarnessAMS session panel beside the Report-figures toggle; absent = the built-in default 100). It rides the D-009 session store and the same rebased persist channel as `report_figs`.
- `batch_submit` reads the run directory's `sweep_config.json`, computes the total point count (cross-product = product of the list lengths, zip = the first list's length), resolves the calling session's field through `exec.agent.id` / the session store (fail-open to the default when the session, the store or the config is unreadable), and REJECTS an oversized scan before anything is staged or uploaded. The reject is the model-facing split rule: an oversized grid becomes multiple Sim batches (auto naming), not one mega-run.
- Submit-time post-check semantics: PEND right after bsub is the expected state — the result reports `state: "queued"` with no warning; RUN without the `.worker_started` marker, a job already EXIT, or an unreadable check produce warnings with wording that says what to do (poll), never "verification failed".

## D-020 — Hand-written run directories; `spectre_pre_check` is the netlist gate inside `batch_submit`

- The recommended workflow's first step is Write: the model hand-authors `template*.scs` + `sweep_config.json` following the dca-cell-design / smart-spectre template contract. `@@P@@` placeholders live on the `parameters` statement ONLY (the sole exemption: `@@temperature@@` on a simulatorOptions line); the circuit references parameters by name. The `spectre_assemble` tool is retired (a thin gen_*.py shell after the scan migration); scripted assembly via a project gen script stays an optional legacy path, run directly with the project root as cwd.
- `spectre_pre_check` (SmartAnaSim, pure JS — no python on the check path, so the submit side needs no local python) validates a run directory: language format, sweep-parameter presence, and the value gates resolved through the check-param chain (D-005; `r = 0` reads as the idiomatic short). The chain's table is `{ rcl, mult, unit_check }` — `bias_check` and `strict_includes` are retired with their check families; the `mult` table (`nf` 1..128, `m` 1..1000, positive integers) is new. Session entries that predate the mult table are dropped entry-level on read — new sessions are the bar.
- `batch_submit` calls the tool automatically before anything is staged, passing the calling session's id explicitly (a nested tool call's exec identity does not reliably flow); findings fail the submit with the error list, `no_pre_check: true` is the explicit waiver (for reviewed failures only), and a missing tool degrades fail-open to a warning. The self-check's preparation runs its staged `gen_selfcheck_rc.py` directly and every submission passes through the same gate.
