# Design Decisions

Persistent, append-only record of design decisions for the `dsh-harnessams` plugin and the HarnessAMS suite. One numbered entry per decision (`D-001`, `D-002`, ...); entries are never rewritten — a decision that changes is superseded by a new entry naming its predecessor. New entries go at the bottom.

Entry template:

```markdown
## D-NNN — <title>

- Status: Accepted | Proposed | Superseded by D-MMM (date)
- Context: why the question existed
- Decision: what we do
- Consequences: what this implies, including the costs
- Alternatives considered: what else was on the table and why it lost
```

## D-001 — Plotly delivery for generated sweep reports

- Status: Accepted (2026-10-27)
- Context: sweep reports (`<project>/Analysis/<project>_report.html`) are interactive Plotly pages opened offline by double-click and also linked from the plugin web UI (served per session at `/harnessams/dash/<sessionId>/…` since D-008; the original `/harnessams/reports/` route was retired with D-009). Plotly.js is a 4.6 MB asset; the `dsh-harnessams` package ships the master copy (`src/assets/plotly.min.js`, also served in-app at `/harnessams/assets/plotly.min.js`). Report generators need a single, stable, relative way to load it — without per-report duplication, without requiring network access at view time, and without depending on a specific install layout.
- Decision: one copy per workspace at `<workspace_root>/assets/plotly.min.js` (workspace root = the directory holding `harnessams.json`). The report generator seeds it on demand from the best local source — an explicit `--plotly` path, an ancestor-probed copy (package-local `assets/`, `src/assets/`, an installed `node_modules/dsh-harnessams` sibling, or a `dsh-harnessams/` directory under a `node_modules` ancestor), or the workspace `plotly_asset` config field — refreshing it when the file size differs (plotly version bump). Every report references it with a workspace-relative `src` (`../../assets/plotly.min.js`), which is always same-drive and survives folder moves within the machine. A one-line `window.Plotly` check falls back to the in-app `/harnessams/assets/plotly.min.js` route when the page is viewed through the plugin's reports route. The CDN (`https://cdn.plot.ly/plotly-3.0.1.min.js`) remains the last-resort fallback when no local source exists (`--plotly-cdn` forces it).
- Consequences: reports are offline-capable by default; exactly one 4.6 MB copy per workspace instead of one per report; the workspace `assets/` directory is a runtime artifact and is not committed (gitignored where a workspace lives inside a repo). Reports only render charts when the workspace tree travels with them.
- Alternatives considered:
  - CDN-only reference: needs network at view time; fails offline and behind
    firewalls.
  - Per-report copy beside each HTML (the previous behavior): self-contained, but
    duplicates 4.6 MB into every `Analysis/` directory.
  - Machine-level shared copy under `$USERHOME/.dsh/profiles/web/node_modules/`:
    relative references cannot cross Windows drive boundaries, and the npm profile
    tree belongs to package lifecycle operations.
  - Direct reference into the installed `dsh-harnessams` package: same cross-drive
    problem, and the reference dies when the package is uninstalled or cleaned.

## D-003 — remoteExecGate: tiered gate for model-initiated remote command execution

- Status: Accepted as a design (2026-10-31, recorded here 2026-11-10); **not implemented** — implementation work is tracked in the top-level repo `dev/todo/remoteExecGate.md`.
- Context: in the default DSH deployment the approval axis idles (the pre-execute waterfall defaults to allow; no `kind:"ask"` producers in the default bundle), so a workspace-write session lets the model run remote commands (`ssh_exec` in the current @linxin666/dsh-ssh channel; `rw_exec` when this decision was written against dsh-remote) with no human gate before execution — the model's blast radius equals the SSH account's filesystem permissions. Static analysis cannot bound a command's effects (Rice's theorem; trivial evasion via variable indirection, command substitution, cd+relative paths, pipes, in-tree binaries, symlinks), so lexical gating is only sound for fixed, argument-free commands. Upstream takes the same position (dsh-remote `lib/remote-sandbox.js`: "a command's effects cannot be bounded lexically… pretending to confine it would be worse than saying we do not").
- Decision: the plugin may register a `ctx.on('tools/pre-execute')` listener gated by a plugin config field `remoteExecGate` with three tiers. `off` (default) — no listener registered; `rw_exec` ungated (status quo; post-hoc audit remains). `whitelist` (recommended) — allow-listed commands pass silently; every other model-initiated remote exec (`ssh_exec`; `rw_exec` at decision time) returns `{kind:'ask', reason, displayReason:{en,zh}}` → approval chain → Web UI prompt; whitelist discipline: fixed argument-free commands only, anchored to the whole command string (no prefix/substring match — blocks `known-cmd; payload` appends), zero write capability (`>`, `tee`, `sed -i`, pipes, `$()`, `;`, `&&` excluded), commands with dynamic paths stay out (they fall through to ask). `ask-all` — every model-initiated remote exec prompts (untrusted deployments/demos; highest friction). A hard-lockdown tier needs no plugin: set the session read-only. (Historical note: under the retired dsh-remote the write fence rejected `rw_exec` outright in a read-only session; under dsh-ssh the exec tools are zero-gated, which is exactly why this gate design stays relevant.) Self-calls are exempt in every tier: the plugin's own check/self-check calls (since D-009 the four Overview buttons funnel through the server-side `harnessams_selfcheck` runner via `POST /api/tool`, not model-initiated exec) and the transfer tools (`ssh_upload`/`ssh_download`; `rw_upload`/`rw_download` at decision time) pass through untouched. Interaction with the approval policy: under the default `ask` policy the gate's asks surface as UI prompts; under `never` (including the `danger-full-access` preset) asks are deterministically rejected — i.e. "outside the whitelist = denied", a coherent unattended posture.
- Consequences: one ~20-line integration point with `dsh-experimental-auto-review` as the in-tree precedent; no user-visible change in the default `off` tier. Until implemented, remote command execution has no pre-execution human gate in any tier. End-to-end behavior is unverified (listener receives model-initiated calls; ask → UI prompt on both approve/deny paths; zero disturbance to the check buttons and the batch chain) — the spike checklist lives with the implementation todo.

## D-004 — JS single implementation for in-plugin functionality; Python confined to three scenario families

- Status: Accepted (2026-11-10)
- Context: the suite's tool shell, server routes, and analysis pipeline are Node by construction (DSH plugins are Node packages), but shipped compute code historically mixed JS and Python freely. By 2026-11-10 the mix had been deliberately reduced — `safe_trash` rewritten as the JS module `src/trash.js` (2026-11-09), the collect/report pipeline ported into `src/tools/sim_analysis.js` (f64410a, 2026-11-10; the original Python kept only as `_dont_use_*` reference copies excluded from the tarball) — leaving exactly three Python pockets, each with a structural reason. Without a written rule, new features would drift back into ad-hoc Python or dual py/js implementations.
- Decision: JS is the default and the single implementation for everything inside the Harness plugins (tool definitions, server routes, analysis/report/trash logic, progress reading, self-check orchestration). Python is used only in three scenario families, one example each:
  1. workers that must run remotely on cluster nodes where Node cannot be assumed (LSF compute nodes are shared Linux hosts; a measured node has no Node installation at all, and the self-check treats "remote node missing" as a fault family) — e.g. `spectre_sweep_worker.py`;
  2. s-parameter numeric computing in the numpy / complex-matrix domain — e.g. `snp_extract.py`;
  3. per-project assembly scripts authored by the user, whose existence as plain project-side scripts is itself the architecture (intermediate steps are not codified) — e.g. `gen_selfcheck_rc.py`.

  Existing shipped scripts in these families stay as-is; new internal functionality lands in JS; introducing a new Python family outside the three requires its own decision entry here.
- Consequences: one runtime per feature inside the plugin — no new dual py/js twins to keep in agreement (the selfcheck verification twins `selfcheck_verify.py`/`.mjs` predate this rule and stay grandfathered). System Python remains a runtime dependency only where the three families need it. Future ports must re-baseline regressions, tolerance-style where floating point differs across runtimes (the collect/report port already paid this cost).
- Alternatives considered:
  - Dual py/js implementations everywhere (the selfcheck pattern as the general rule): doubles maintenance and invites contract drift; kept only as the legacy selfcheck exception.
  - Full de-Pythonization (porting snp and the sweep worker too): rejected — cluster execution structurally requires Python on the remote side (family 1), and the numpy/complex-math domain plus regression re-baselining make family 2 cost-ineffective; assembly scripts (family 3) are user-authored assets, not plugin code, so they cannot be "ported" at all without changing the authoring model.
  - All-Python: rejected — DSH hosts always have Node, so JS keeps the plugin single-runtime wherever the plugin itself executes.

## D-005 — Per-session task selection, sidebar default-open, and the no-horizontal-scroll / 8-line-clamp UI rules

- Status: Accepted (2026-11-18); the task-selection storage aspect was superseded by D-008 (2026-11-19) — the default-open and scroll/clamp rules remain in force
- Context: three user rulings landed together as one UI wave. (a) Every plugin surface must live within the window width (no horizontal scrollbars) and read-only text over 8 rendered lines auto-collapses. (b) The selected task capsule binds to the SESSION (the task list stays workspace-shared; a forked session inherits the selection). (c) A session whose project already has a `.harnessams` store gets the HarnessAMS sidebar opened on first sight — new sessions, cross-project switches, and returning to the start window — without fighting an explicit user close. Two earlier positions are superseded: 2026-10-25's "sessions deliberately not modeled" (still true for the task LIST, now false for the selection) and 2026-11-10's "a fresh session starts collapsed" (now a per-project default-open).
- Decision:
  1. Strip selection storage moves to a per-session localStorage map `hams-task-strip-sel-v2` (`{sessionId: 'overview'|taskId}`, pruned to the 50 most-recent entries; the old single-value key seeds exactly one unseen session during migration). First-seen sessions with no entry inherit the LAST ACTIVE selection (module memory, not parent lineage — see the limitation below) and persist it as their own entry. The sub-view preference `hams-task-view` stays browser-global.
  2. Default-open lives in the conversation-header button (the only always-mounted consumer): on a sessionId change, after the existing 1.5 s open-state tracking check, it opens the tab iff the session's host layout record shows NO tabs ever hosted (`dsh.sidebar-right.v1.<sessionId>` value's `layout.nodes.*.tabs` all empty — the host writes the key at session creation, so key-existence is NOT "touched") AND `/api/project` reports `initialized` (workspace has `.harnessams`; the field is served by `sessionProject`). Blank sessions are not accounted in the workspace registry until their first turn, so the mapping gets a bounded silent retry (~2 min). One attempt per session per page lifetime; the untouched gate is re-checked right before opening.
  3. Scroll/clamp rules: the task tab's `.hams-body` is the ONLY scroll container (`overflow-y: auto; overflow-x: hidden`); `ProjectOverviewView` is plain flowing content (`flex: none`, no nested `.hams-body`/height chain — the old nesting starved the overview of its scrollbar); the task branch grows (`flex: 1 0 auto`) instead of clipping. All roots (`.hams-page/.hams-body/.hams-dialog/.hams-tc`), table cells, and `.hams-pre` carry `overflow-wrap: anywhere` (pre also `word-break: break-all`); read-only long text renders through `ClampText` (8-line max-height clamp with a measured show/hide toggle; editable textareas and tables are exempt — tables wrap instead).
  4. Native `<select>` popups follow the theme via `color-scheme: light dark` plus `option { background: canvas; color: canvasText }` — bg/text resolve from the same scheme as a matched pair, fixing the options-only-readable-on-hover bug.
- Consequences: the open-state probe now requires a viewport intersection AND non-hidden visibility (0.2.2-rc.3 collapses the pane off-viewport with `visibility: hidden` while `offsetWidth` stays non-zero — the old offset-based probe false-positived and re-opened collapsed sidebars). Known limitations, revisitable when the host grows read faces: (i) fork-parent lineage is NOT directly readable — the client-side `sessions` service a plugin ctx sees is an unconnected instance (list snapshot stays empty forever, verified live) and the server-side `sessionController` facade exposes no list face — so inheritance means "continue the last active selection", which covers fork-then-switch and new-session continuation but not e.g. jumping to an unrelated old fork; (ii) a page reload that lands on a never-touched BLANK session in an initialized project cannot auto-open (blank sessions mount neither the tab body nor the conversation-header actions; the first user turn mounts the header and the open fires then).
- Alternatives considered: server-side `/api/session-parent` endpoint (dropped — no host read face to power it); inheriting via the sessions catalog parent links (dropped — unconnected instance); auto-open in the tab body (dropped — never-mounted for untouched sessions); auto-open on every switch into a qualifying project (rejected by the user — an explicit close must win until another session is entered).

## D-006 — Round-2 refinements: exclusive task binding, blank-session default-open, console-page scroll, fixed-layout tables

- Status: Accepted (2026-11-18, same day as D-005; supersedes the inheritance-exclusivity and blank-session aspects of D-005, keeps the rest); the exclusivity/task-binding aspects were later superseded by D-007 (2026-11-18) and D-008 (2026-11-19) — the console-page scroll and fixed-layout-table rules remain in force
- Context: user round-2 feedback on the D-005 wave. (a) "One task must not be bound to multiple sessions" — the v2 map + inherit-and-persist model let a fork child and its parent both hold the same task. (b) A NEWLY CREATED blank session must open the sidebar immediately, not after its first turn (D-005 accepted the header-actions mount which only a first turn brings). (c) The disk-usage listing lives on the tier-1 console page, whose `.hams-page` relied on the host main panel for scrolling and got clipped past one screen. (d) The settings table still overflowed the pane: `<select>` intrinsic widths and a nowrap name column are immune to `overflow-wrap`.
- Decision:
  1. Exclusive binding: `rememberStripSel(sessionId, task)` now rewrites every OTHER session holding that task to `'overview'` (pinned back, not deleted — a released session must read its own entry on return instead of re-inheriting and re-stealing via the last-active fallback). One task belongs to exactly one session: whichever session selects it last holds it.
  2. Blank-session default-open: `apply()` polls localStorage for NEW `dsh.sidebar-right.v1.*` keys (the host mints the key at session creation/first activation, so a new key = "a never-seen session just went active"; same-page storage events do not fire, hence the 1 s poll). Each new key runs the same initialized/untouched policy; while the mapping is still "not accounted", the module-level `lastProjectInfo` answers (a new session is created under the CURRENT workspace).
  3. `.hams-page { height: 100%; box-sizing: border-box; overflow-y: auto }` — the console page scrolls itself regardless of the host main panel.
  4. `.hams-table { table-layout: fixed }` + `.hams-table .hams-select { max-width: 100% }` + dropped the nowrap name cell: fixed layout ignores content min-content, so selects and long cells can no longer push tables past the container.
- Consequences: task selection now migrates with the active session only on an explicit click or a first-seen inheritance; released sessions come back to the project overview. The 1 s key-poll runs for the page lifetime (cheap; primes on load so pre-existing keys never trigger). Verified live (IAB 1920×1080, port-isolated fresh origin): 720px-viewport console page scrolls (1567>720), settings table zero horizontal overhang at 864px body width, new blank session opens within ~2 s of creation, fork-child inheritance re-pins the parent to overview and the parent stays there on return.

## D-007 — Per-session ACTIVE TASK LIST with fork inheritance and sessions.json persistence

- Status: Accepted (2026-11-18, round 3; supersedes D-006's exclusivity aspect and the single-selection model of D-005); the task-list model was superseded by D-008 (2026-11-19) — the sessions.json persistence survives in v2 form
- Context: two rounds of single-selection models missed the user's actual mental model. Round 3 ruling: every session maintains an ACTIVE TASK LIST (multiple tasks highlighted at once, one of them displayed); a fork/new session inherits the previous session's list; the state MUST survive a reload (disk file) — "if no file can hold the state, keep a sessions.json".
- Decision:
  1. State model: per session `{ active: Set<taskId>, display: 'overview' | taskId }`. Capsules in the active set carry the `active` class; the displayed one additionally carries `cur`. Clicking a capsule activates+shows it; clicking the currently-shown active capsule toggles it OUT (back to overview). New tasks enter the active set on creation. Deleted tasks drop out via sanitize (display falls back to overview when its task disappears).
  2. Inheritance: a first-seen session (no entry anywhere) copies the previously ACTIVE session's list — fork-then-switch and new-session continuation both land there (the host still exposes no parent-session read face; the v4 session header and projcache carry no parentSession either, verified on disk).
  3. Persistence: `<workspace>/.harnessams/sessions.json` (`{ version, sessions: { [sid]: { active, display } } }`). Server: `readSessionTasks` (missing/corrupt → empty, never throws) + `writeSessionTaskState` (read-modify-write of ONE session's entry — never a full-file clobber; insertion-order pruning at 200 sessions, 50 active ids each; display must be 'overview' or a member of active). Routes: `GET /api/session-tasks` (whole map, hydrated once per project per page life) + `PUT /api/session-tasks` (`{sessionId, state}` merge). Client: module map is the runtime truth, every mutation merge-PUTs; first-sight inheritance is persisted immediately; blank sessions keep theirs in memory until the workspace mapping lands (then the projectPath change re-adopts and persists).
- Consequences: multiple sessions MAY share active tasks again (inheritance copies the list — D-006's exclusivity is gone by design). Reload restores every session's list from disk; closed/archived sessions leave stale entries behind (harmless; pruned by the 200-entry cap). localStorage plays no role in task selection anymore (`hams-task-strip-sel*` keys are simply abandoned in place).
- Alternatives considered: true lineage via parentSession (dead end — v4 header/projcache carry none, plugin ctx services have no list face); localStorage persistence (rejected — the user wanted a disk file in the workspace).

## D-008 — Task retirement: every session is a work unit (per-session dashboard + check params), fork-copies are deliberately branch-point-independent

- Status: Accepted (2026-11-19; supersedes D-007's task-list model, D-006's exclusivity aspect, and D-005's task-selection storage — the sidebar default-open and scroll/clamp rules of D-005/D-006 survive untouched)
- Context: user ruling (tasks are pointless — merge the work units into sessions): the task concept is retired. The sidebar strip becomes exactly two entries (project overview + THIS session's panel, no creation button, no task name/description); the session panel keeps only the Dashboard and Checks sub-views (the sim-settings placeholder is deleted). Each DSH session is now the work unit and carries its own dashboard reports and CONFIRMED check parameters — the latter is a deep refactor the user explicitly chose over the cheap project-shared option. A brand-new session starts EMPTY; a FORKED session gets a copy of the session config — and that copy is DELIBERATELY designed to be independent of the branch point (a design stance, not an approximation): the fork parent is not identified (rc.3 ordinary forks carry no parentSession by design) and no branch-cut state is reconstructed; the copy source is the currently-last-active session (page lifetime) or, failing that, the most recently written sessions.json entry, and the copied content is that source's CURRENT snapshot.
- Decision:
  1. Store: `<workspace>/.harnessams/sessions.json` v2 `{ version: 2, sessions: { [sid]: { display: 'overview'|'session', reports[], dashboard_selected, check_params? } } }`. A v1 file parses as EMPTY (clean break — its entries reference task ids that no longer exist; existing workspaces hold zero reports and zero check_params, so nothing was lost). Legacy tasks.json/check_params.json stay on disk unread; check_params.json is demoted to the project-level FALLBACK. Server: `readSessionConfigs`/`writeSessionConfig` (single-session read-modify-write merge, 200-entry insertion-order pruning, reports normalized by the old task rules, check_params validated by the old checkparams rules). The `.harnessams`-creation AGENTS.md-template duty moves to writeSettings + writeSessionConfig (writeTasks/writeCheckParams retired).
  2. Session identity in tools (probe-verified live, harnessams-workspace/probe-taskmerge-20261119): `exec.agent.id` IS the SessionId (`dsh-tools contracts.d.ts` → `dsh-agent` `Agent.id: SessionId`, "Session-backed Agent identity") and the shell-env built-in `DSH_SESSION_ID` carries the same id into every model bash/pwsh call. sim_analysis(report=true) therefore registers the generated report EXACTLY into the calling session (`exec?.agent?.id`; absent identity → visible register_error, never a wrong target; the old `task=<id|name>` parameter is gone). Known boundary: a subagent is its own session (origin 'subagent') — its registrations/checks land on its own entry; same worldview as the snp-guide gating.
  3. Fork detection: rc.3 ordinary forks carry no parentSession anywhere a plugin can read (header/projcache/list rows — the controller README states forks are created "without parentSession"); the ONLY durable signal is the inherited cut marker the fork seed writes into the child's own log: event `{type:'session/end-seed', data:{inherited:true}}` (`dsh-session buildForkSeed`). `server/forkdetect.js` zstd-decompresses `<DSH_HOME>/sessions/*/<sid>/session.v4.jsonl.zstd` and matches that predicate exactly — RESUMED sessions also write end-seed events WITHOUT the flag, so the flag, not the event type, is the discriminator (live-verified both ways). Everything fails open to "not a fork". The verdict is served by `GET /api/session-config` ONLY while the asking session has no entry (an entry — including the first-seen write — is the tombstone that stops re-detection).
  4. First-seen flow (client): a session not yet in the module map GETs `/api/session-config`; `fork:true` → deep-copy the copy source's whole entry (reports + check_params + display); otherwise start empty; either way the entry is PUT immediately (tombstone/copy lands at once). Two live-caught bugs shaped the final form: the initial useState must READ the map without INSERTING (a pre-inserted empty entry makes the fork split unreachable), and the copy source needs a store fallback (a reload that lands directly on the fork child has no page-lifetime last-active session — the fallback is the sessions.json insertion-order tail, i.e. the most recent writer, which in the normal flow is the fork source).
  5. Per-session check params, effective chain: `read_check_params(start_dir)` resolves built-in defaults ← project check_params.json ← the calling session's confirmed table (sessions.json), keyed by DSH_SESSION_ID. The env reaches Python through two channels: the host shell-env built-in (model-run bash/pwsh, incl. gen scripts) and the SmartAnaSim tool shells passing `exec.agent.id` via `runPython`'s new env-merge (spectre_assemble/spectre_run_sweep/spectre_parse/snp_read/snp_extract; spectre_assemble threads it through runAssembly's extraEnv). The sidebar's check sub-view edits the SESSION's table (`/api/session-config`; the unconfirmed state shows the project∪built-in fallback as grey ghost values plus a source line); the retired `/api/check-params` routes answer 404/405 with a pointer. Self-check runs the assembly through a direct server-side tool call (no agent in exec) and therefore uses the project-level fallback — consistent with it being a project health check.
  6. Routes: `/api/tasks` (GET/PUT) and `/api/check-params` (GET/PUT) retired; `/api/session-tasks` renamed `/api/session-config` (GET returns the whole map + fallback_params + fork-when-unentered; PUT merge-writes one entry); `/api/report-stat?sessionId=&reportId=`; `/dash/<sessionId>/<reportId>/…` (resolveReportFile reads the session store; directory fencing unchanged).
- Consequences: the strip has no creation/deletion surface; sessions have no names (the capsule reads "Session" with the full id in the tooltip). Reload restores every session's panel from disk; the sub-view preference stays browser-global (`hams-task-view`). Cross-session report sharing now happens only through the fork copy (each session's list is its own). Verified live (IAB 1920×1080, dev-mount --patch): two-entry strip, empty start for brand-new sessions, fork child copies report + confirmed R range, sim_analysis registers into the exact calling session, session A's R=[0.01,1e6] effective in its own shell runs while session B resolves [0.1,1e6] from the fallback, refresh restores everything; AMS 94/94, SIM 34/34.
- Alternatives considered: project-shared check params (rejected by the user — sessions are the work units, different work lines want different check strictness); copying per-key at the branch cut via log reconstruction (rejected — branch-point state is deliberately NOT reconstructed); heartbeat/last-active-registry for tool registration (dropped once exec.agent.id proved exact); agent.id-keyed store without the sessionId bridge (unworkable — the client only knows sessionIds).

## D-009 — Single per-project config (workspace_config.json), the harnessams_selfcheck tool, and artifact cleanup

- Status: Accepted (2026-11-19; retires the family harnessams.json whole — its discovery walker, remote_machines map, workspace_root/pdk_lib/pdk_name/remote_python/remote_node/remote_scripts_dir keys — and fixes the last_selfcheck path mismatch)
- Context: user rulings in three steps. (1) The four Overview buttons should be thin parameterizations of ONE self-check tool that also accepts project settings (agent-controlled configuration), and the stale `last_selfcheck: null` bug must close. (2) All config consolidates into a single per-project file named `workspace_config.json`; the remote root lives THERE (strict UI = config = AGENTS.md interlock, no divergence); the settings table becomes staged with a confirm button and a red "unsaved" status column; AGENTS.md drops the machines section and flattens to one yaml level. (3) Existing state is NOT migrated: `.harnessams` and `harnessams.json` are archived with an `_old` suffix and everything starts fresh. Root cause of the null bug: selfcheck.js wrote runs to the FAMILY root (`<family>/selfcheck/`) while agentsmd.js read `<project>/selfcheck/` — a done run finished one second before a save and the table still wrote null.
- Decision:
  1. `harnessams_selfcheck` tool (src/tools/selfcheck.js): actions `run` (background start, returns run_id) | `status` (one run, project-fenced) | `env` (local facts + probe rows, read-only) | `save_agentsmd`. An optional `settings` object is validated and written BEFORE the action runs — the single config write face for the UI confirm button and for a conversational agent. Session identity follows D-008's `exec.agent.id ≡ SessionId` precedent; an explicit `project` argument must be a registered workspace (errors list candidates). The four buttons ride `POST /api/tool {sessionId, action, settings?, run_id?, lang?}` which resolves the project and calls the same runner; every action button commits pending table edits, so the UI can never diverge from the file.
  2. Config consolidation: `<project>/.harnessams/workspace_config.json` `{ version, workspace: { sim_scripts_dir, plotly_asset, trash_dir }, settings: { run_mode, machine_id, remote_root, remote_dir, scheduler, simulator, compute_script_local, compute_script_remote } }`. The workspace section is laid down once with resolved defaults at file creation (scripts root = the sibling SmartAnaSim package — PKG_ROOT is `<plugin>/src`, so the sibling is TWO `..` levels up; path.join folds `..`, the one-level form silently produces `<plugin>/SmartAnaSim/scripts`, caught live) and survives settings writes read-modify-write; runtime defaults keep everything fail-open (env `HARNESSAMS_SIM_SCRIPTS_DIR` still overrides; plotly falls back to the package copy then CDN; trash defaults to `<project>/.harnessams/trash`, anchored at the target path's nearest `.harnessams`). check params stay OUT (D-008: session table + project check_params.json fallback, untouched).
  3. ## D-010 — Browse-only remote root, self-check stop, and the system-prompt waiting policy

- Status: Accepted (2026-11-21; supersedes the D-009 browse rule "missing root → 409")
- Context: the user's UI feedback list plus the 100 s dumb-sleep incident. - Decision:
  1.   2. Browse bootstrap + symlinks: with no saved root the listing starts at the machine's `$HOME` (`echo -n "$HOME"`), so the picker works before any root exists (the input it replaced was the only other way); the listing command is `ls -1pL … 2>/dev/null || ls -1p …` so symlinked DIRECTORIES survive the dirs-only filter (node1's real tree hides behind `~/simulation -> /prjtemp`, live finding; the plain-listing fallback keeps a stray broken symlink from failing the request).

  5. Observability: submitStep detail is failure-first (the error text is the headline; a leftover job record from the other attempt demotes to an annotation); pollStep streams live counts into its own step row (⏳ in-flight rows render in the steps table; the 3 s status poll picks them up).
