# Design Decisions

Design decisions for the `dsh-harnessams` plugin and the HarnessAMS suite. **Ordered by importance, not chronology** (2026-11-23 ruling): the top entry is the suite's division of labor; everything else follows in the order a maintainer needs it. Entry IDs (`D-001`…`D-018`) are stable — external documents cite them. Superseded content folds into its successor entry; the day-by-day history lives in the root repo's `docs/` chronicle.

Entry shape: Status / Context / Decision / Consequences (long Alternatives sections were dropped in the 2026-11-23 compression; the distilled trade-offs remain inside Decision/Consequences).

## D-018 — Suite division of labor: SmartAnaSim is a pure standalone tool set; HarnessAMS owns the managed scan flow (2026-11-23)

- Status: Accepted (2026-11-23; supersedes D-013's "SmartAnaSim carries no bundled skills", D-016's three-tool card scope, and the sim-progress placement of the 2026-11-01 tool redistribution)
- Context: the 2026-11-01 redistribution left scan execution split across packages (SmartAnaSim's local spectre_run_sweep vs the top plugin's remote batch_*) with the progress/report tools in the top plugin, while the requirement repo placed "run simulation" wholly with SmartAnaSim. User ruling 2026-11-23: two clean positions, scan methodology centralized.
- Decision:
  1. **SmartAnaSim is a pure tool set, usable on its own** — no other plugin required, and zero references to any other plugin's tools in its tool descriptions, file headers or skill text. Its spectre capability is limited to template generation + configuration checks (`spectre_assemble`); the `snp_*` family stays; the sweep worker and analysis scripts are script-face — **data processing is not tool-shaped** (the `spectre_run_sweep` and `spectre_parse` tools retired; 0.1.0 was never published, no aliases). It carries exactly one bundled skill: `smart-spectre`, the spectre configuration reference — a root page (template rules, assembly checks, run-directory contract, worked example = the RC self-check testbench) plus named companion pages (worker-config, analysis-scripts, s-params, cascade, pss-variant).
  2. **HarnessAMS provides the standardized, process-oriented scan methodology.** `batch_submit` gains `scheduler="local"` (detached background worker on this host; submit returns immediately, poll with batch_poll) beside `direct` (SSH target host, foreground) and `lsf`. `batch_poll` absorbs `batch_fetch`: a terminal poll (completed/failed/partial) pulls the fixed light set — `sweep_progress.json` + `errlog.txt` — straight down per file (no includes, no archive; raw psf/sp data stays remote by design, deep analysis runs on the host that holds it) and every frame carries a bounded per-point digest (index/name/status/params). `sim_progress` retires outright; `gen-sweep-report` renames to `gen_sweep_report`. `overwrite: true` clears the stale replay markers (`.hams_submitted`/`.hams_direct_done`) under the flock and tags the fresh markers, so a finished batch actually re-runs while a replay of the same overwrite call still short-circuits. `snp_extract` accepts only the params CSV `snp_read` writes (lossless `%.17g` round trip). Tool faces: 4 (SAS) + 5 (AMS).
  3. **The skill catalog splits along the same line**: `batch-sweep` (generic scan methodology — schedulers, Sim naming, poll semantics, remote-first analysis, the report spec flow) replaces smart-spectre in HarnessAMS; the dca skills keep their spectre-language content and sky130 examples in place and point at batch-sweep/smart-spectre for the mechanics.
- Consequences: `batch_poll` carries the only progress card (a local submission is polled through the same run directory, so local scans keep live cards); the project self-check's local chain drives batch local and runs the parser script directly; SmartAnaSim standalone = assemble + scripts + its skill, the suite adds the managed flow. The requirement repo's wording ("run simulation" wholly under SmartAnaSim, HTML report in its function list) knowingly diverges — reconcile at the v0.1.0 release-notes pass. D-013's single-homed catalog rule inverts: each package now carries the skill for its OWN surface (one catalog line each side).

## D-004 — JS single implementation for in-plugin functionality; Python confined to three scenario families (2026-11-10)

- Status: Accepted
- Context: shipped compute code historically mixed JS and Python freely; without a written rule new features drift back into ad-hoc Python or dual py/js twins.
- Decision: JS is the default and the single implementation for everything inside the Harness plugins (tool definitions, server routes, analysis/report/trash logic, progress reading — the run-directory ladder lives in `src/progress_files.js`, shared by the endpoints and the batch tools — self-check orchestration). Python only in three families: (1) sweep workers that must run where Node cannot be assumed (cluster nodes) — e.g. `spectre_sweep_worker.py`; (2) S-parameter numeric computing in the numpy/complex-matrix domain — e.g. `snp_extract.py`; (3) per-project user-authored assembly scripts, whose existence as plain project-side scripts is itself the architecture — e.g. `gen_selfcheck_rc.py`. A new Python family needs its own decision entry.
- Consequences: one runtime per feature; the selfcheck verify twins (`selfcheck_verify.py`/`.mjs`) are the grandfathered exception. Ports must re-baseline regressions, tolerance-style where floating point differs.

## D-009 — Single per-project config (workspace_config.json) + the harnessams_selfcheck tool + artifact cleanup (2026-11-19)

- Status: Accepted
- Context: config sprawl (family harnessams.json, remote_machines map, split UI/config/AGENTS.md sources) plus the last_selfcheck path-mismatch bug. User rulings: one tool behind the four Overview buttons; one config file per project; NO state migration — old files archived `*_old`, fresh start.
- Decision: `<project>/.harnessams/workspace_config.json` `{ version, workspace: { sim_scripts_dir, plotly_asset, trash_dir }, settings: { run_mode, machine_id, remote_root, remote_dir, scheduler, simulator, compute_script_local, compute_script_remote } }` — the workspace section laid down once with resolved defaults (scripts root = the sibling SmartAnaSim package; PKG_ROOT is `<plugin>/src` so the sibling is TWO `..` levels — path.join folds `..`, the one-level form silently misses), settings survive writes read-modify-write; env `HARNESSAMS_SIM_SCRIPTS_DIR` overrides. remote_root is a settings field fencing every remote_dir (resolveMachine takes it explicitly; `HARNESSAMS_REMOTE_MACHINES` retired). `harnessams_selfcheck` actions run/status/stop/env/save_agentsmd + optional `settings` write-before-action — the single config write face, ridden by the UI buttons through `POST /api/tool`. Runs live under `<project>/.harnessams/selfcheck/<runId>` (project-fenced reads); a clean run's artifacts are deleted at finalize, failed runs keep evidence, the next run cleans history; finalize re-syncs AGENTS.md unconditionally. check params stay OUT (D-008).
- Consequences: fresh projects need one confirm click; agents reconfigure + verify in-chat through one tool; legacy state on disk is archived, never read.

## D-008 — Task retirement: every session is a work unit; fork copies are branch-point-independent (2026-11-19)

- Status: Accepted (supersedes D-005's task-selection storage, D-006's exclusivity, D-007's task-list model)
- Context: user ruling that tasks are pointless — the task concept retires; the deep refactor (per-session confirmed check params) was chosen over the cheap project-shared option.
- Decision: sidebar strip = exactly project overview + THIS session (Dashboard + Checks sub-views). Store `<workspace>/.harnessams/sessions.json` v2 `{ display, reports[], dashboard_selected, check_params? }` per session (v1 parses as empty — clean break); single-session merge writes, 200-entry pruning. **Session identity: `exec.agent.id` IS the SessionId** (probe-verified) and `DSH_SESSION_ID` is a shell-env built-in — tools thread it through runPython's env-merge so per-session check params resolve in every worker (chain: built-ins ← project check_params.json ← session table). Fork detection: rc forks carry no parentSession; the ONLY durable signal is the inherited end-seed marker in the child's zstd session log (`server/forkdetect.js`); fork copies take the currently-last-active session's CURRENT snapshot, deliberately branch-point-independent; served only while the asking session has no entry. New sessions start empty.
- Consequences: no task creation/deletion surface; cross-session report sharing happens only through the fork copy; subagents are their own sessions.

## D-012 — gen_sweep_report is a pure report renderer; RawResults/SimResults/Figs layout; remote-first analysis (2026-11-21)

- Status: Accepted (tool renamed `gen_sweep_report` 2026-11-23, D-018)
- Context: sim_analysis did too much (collect/summarize/curves/report) and the Retry report's all-dashes table exposed the real issue — raw-data processing belongs to the model, so the tool only draws.
- Decision: input = a model-written spec JSON `{project_dir?, title?, conclusions?, out?, rounds:[{id, title?, points, curves?, note?}]}` (points/curves inline or `{"$file"}` refs; project_dir derives when the spec sits in `<project>/SimResults/`; column names = the union across points; the cellVal param branch reads `p.params`). Output: report at the project root, data JS in `SimResults/`, one PNG per chart in `Figs/` (headless jsdom + bundled plotly + `Plotly.toImage(svg)` + resvg rasterization — the PNG path never settles in jsdom; deps ship prebuilt, export is fail-open). Registers into the CALLING session's dashboard (exec.agent.id). File layout both sides (user ruling "remote+local same name"): batch_submit auto-names `<remote_root>/RawResults/Sim*`; raw local data lands `<project>/RawResults/`; compact results go to `SimResults/` via ssh_download. **Remote-first analysis** = the put/exec/get triple over dsh-ssh (upload the SmartAnaSim parser scripts side by side or a self-written analyzer, exec with the cluster's full python path, download the compact JSON); the batch-sweep skill documents it as the default. Fork-404 fix rides along: the first-seen persist is awaited before the dashboard iframe mounts, with bounded retries.
- Consequences: the Analysis/ era and the collect results.json contract ended for new flows; the model owns all data processing; every chart exists as a standalone PNG at generation time.

## D-011 — Bundled skills + the template*.scs family + the Sim run-dir convention (2026-11-21)

- Status: Accepted (the report-redesign section was superseded by D-012; the skill ownership split was superseded by D-018)
- Context: the simulation-analysis wave — skills bundled into the plugin, the exact template.scs name relaxed, a Sim naming convention, a generic sweep report.
- Decision: skills ride the official host registry — `ctx.skills.register` per packaged `skills/<name>/SKILL.md` (frontmatter name/description; catalog lines only, bodies load on demand through the host `skill` tool; `resourceBase` = the skill directory; fail-open; `inject` carries `skills`). template*.scs family: the file uploads under its OWN name and `sweep_config.netlist_template` must match it exactly (mismatch/undeclared/declared-but-missing fail at submit). Sim convention: `nextSimDir` (`Sim<N>_<YYYYMMDD>_batch<M>`; same index + batch+1 same day, else index+1 batch1); `batch_submit.remote_dir` optional — one `ls -1` picks the next free name under `<remote_root>/RawResults`; the progress layer recognizes `<project>/Sim*/` and `sweep/Sim*/` beside legacy `sweep/RoundN/top`. dca method: shunt-arm total from ideal formulas, switch Ron a DIRECT input (1/3..1/5 of the arm total), ZTC retired, ideal R/C with real sky130 switches, simulation authoritative over analytic predictions.
- Consequences: skill catalog lines reach every session on an enabled plugin (wire-verified); the dca data pack ships under the skill with provenance notes.

## D-016 — Live progress cards: instant first frame + the remote poll endpoint (2026-11-22)

- Status: Accepted (the three-tool card scope was superseded by D-018: batch_poll is the only carded tool)
- Context: the 2026-11-22 session-log investigation found remote batches never showed live progress — `/api/progress` reads only local files and a 1 s poll snapshot left the real run happening between tool calls. User rulings: a carded call must show content the MOMENT it is invoked (zero-ssh first frame); a batch finishing between polls still shows both frames.
- Decision: `readRunProgress` ladder gains the `.batch_job.json` rung (progress → .worker_started → job → config) — a submitted-but-unmirrored run dir answers an instant 0/N submitted frame. `GET /api/progress-remote`: same session fence; machine/dir/job resolved server-side from the job file; runs the batch pollCommand through execRemote (10 s); failures answer `200 {unreachable}` so the card keeps its last frame; 4 s TTL single-flight per runDir bounds ssh pressure. Client: the batch_poll card fetches the remote source at the 5 s wait-policy cadence plus the local ladder each tick (normRemoteProg normalizes shapes). `batch_poll` gains `wait_sec` (default 0 = snapshot contract unchanged; re-poll ~10 s until terminal or ≤600 s, last payload wins) — the blocking call is the live-card window.
- Consequences: fixture protocol notes for custom workers — must accept `--work-dir`, write progress atomically WITH a trailing newline (a missing `\n` splices the poll sections; section() now tolerates it, regression-tested). REMOTE_WAIT_POLICY and the skill Monitor sections carry the cadence rules.

## D-017 — spectre_parse keeps its standalone .sp entry; sp.sp stays with the snp_common parser (2026-11-23)

- Status: Accepted (recorded by a parallel session — AMS 938b8b4 + SAS c9bd7b3, unpushed; the TOOL wrapper itself was retired later the same day by D-018 — the entry and the delegation survive unchanged in `spectre_psf_parse.py`, documented by the smart-spectre skill's analysis-scripts page)
- Context: a code-review proposal to merge the standalone `.sp` file entry (`--raw-dir` pointing directly at a file, outputs landing beside it) into the generic psfascii swept-curve parser.
- Decision: keep the entry and the delegation to `snp_common.parse_psfascii`. Three reasons: (1) no new dependency — the entry rides the directory mode's existing delegation, the upload tree is unchanged (the worker already carries snp_common transitively); (2) sp.sp is format-special — the HEADER carries a port table (`PORT<k>:r` / `PORT<k>:num`; Spectre uppercase 0-based vs EMX lowercase 1-based) and TYPE holds S/Y/Z side by side, which the generic `_parse_swept` would flatten three-ways (signals ×3), drop the port renumbering (silently permuting matrices on out-of-order files) and turn hard errors into NaN fills; (3) the snp tools are guide-gated — a session that has not called snp_guide has no bare .sp reader, and snp_read's output contract (matrix long CSV + `_read.json`) is not the `<stem>_psf.json` Re/Im curve JSON.
- Consequences: the generic parser mechanically CAN parse sp.sp — the risk is silent semantic corruption, not a crash, and merging would create a second sp parser in the tree. Directory mode already folds each point's sp.sp into its output; the ruling concerns the standalone-file entry only. Changing `spectre_psf_parse.py` must keep the delegation structure.

## D-010 — Browse-only remote root, self-check stop, the system-prompt waiting policy (2026-11-21)

- Status: Accepted (supersedes D-009's "missing root → 409" browse rule)
- Context: the UI feedback list plus the 100 s dumb-sleep incident; user ruling that waiting guidance belongs in the SYSTEM PROMPT.
- Decision: remote_root is set ONLY through the dsh-ssh browse picker (no free-typed row; no saved root → bootstrap at the machine's `$HOME`; `ls -1pL` with a plain-listing fallback so symlinked directories survive). Per-row out-of-sync marker (draft vs settings per key) with a 1 s follow poll — external writes appear within a second, fresh sessions never paint red. `harnessams_selfcheck` action=stop: flips the cancel flag, aborts in-flight tool calls (AbortSignal.any with the timeout), bkills LSF jobs best-effort, finalizes `cancelled` with evidence kept — never enters last_selfcheck_*. Submit-step details are failure-first (stale job records demote to annotations); poll steps stream live counts into their step row. `ctx.systemPrompt.section('harnessams:remote-wait-policy', order 5500)` — static English, KV-stable; inject must declare systemPrompt (cordis throws on undeclared ctx access; optional chaining cannot save it).
- Consequences: browsing is the only root-setting path; every session on an enabled HarnessAMS carries the waiting policy (wire-verified).

## D-015 — The AGENTS.md config block renders the settings-matched self-check workflow (2026-11-21)

- Status: Accepted (branch texts follow the tool surface — the 2026-11-23 wave reworded all five chains to the batch-local/script-parse vocabulary)
- Context: the block carried measured values but not HOW to work under the configuration; the user asked for the feasible run_mode × scheduler × simulator combinations as explicit tool-call-order workflows, saved as the branch matching the current settings.
- Decision: `server/selfcheckWorkflow.js` renders one of FIVE feasible branches (local/spectre, local/golden, remote/LSF/spectre, remote/direct/spectre, remote/golden; compute languages interpolate, never fork): a session-face bullet (run → status poll → stop), the chain bullet in tool-call order, the branch's fallback rule, a shared finalize bullet. English + ASCII by the block's language ruling; unknown settings normalize to defaults. Inserted on VALUES builds only (the first-fill template renders none); both save paths (save_agentsmd and the finalize auto-sync) share one change point.
- Consequences: the block grows ~10 lines per config (only the matching branch); re-syncing under different settings switches the branch in place.

## D-003 — remoteExecGate: tiered gate for model-initiated remote command execution

- Status: Accepted as a design; **not implemented** — tracked in the root repo `dev/todo/remoteExecGate.md`
- Context: in the default DSH deployment the approval axis idles (pre-execute defaults to allow), so a workspace-write session runs remote commands with no human gate; static analysis cannot bound a command's effects (Rice's theorem; upstream takes the same position), so lexical gating is only sound for fixed, argument-free commands.
- Decision: a `ctx.on('tools/pre-execute')` listener gated by a plugin config `remoteExecGate` with three tiers: `off` (default, status quo), `whitelist` (recommended — fixed argument-free allow-listed commands anchored to the whole command string, zero write capability; everything else asks; under a `never` approval policy "outside the whitelist = denied"), `ask-all`. Self-calls are exempt in every tier (the plugin's own check/self-check funnel and the transfer tools). A hard lockdown needs no plugin: set the session read-only.
- Consequences: one ~20-line integration point; until implemented there is no pre-execution human gate in any tier.

## D-001 — Plotly delivery for generated reports (D-002 folded in: source-choice at init, deferred)

- Status: Accepted (2026-10-27); the D-002 source-selection step remains deferred — urgency lowered once D-009 pinned the default source as the workspace `plotly_asset` field
- Context: reports are interactive Plotly pages opened offline by double-click and served per session through the plugin dashboard; plotly.js is a 4.6 MB asset needing one stable relative reference without per-report duplication or view-time network.
- Decision: one copy per workspace at `<workspace_root>/assets/plotly.min.js`, seeded on demand from an explicit `--plotly` path, an ancestor-probed package copy, or the workspace `plotly_asset` field (refreshed on size change); reports reference it workspace-relatively, with an in-app `/harnessams/assets/plotly.min.js` fallback when viewed through the dashboard route and the CDN as the last resort (`--plotly-cdn` forces it).
- Consequences: offline-capable by default; exactly one copy per workspace (runtime artifact, not committed); reports render charts only when the workspace tree travels with them.

## D-005/D-006/D-007 — UI layout & session-surface rules (merged 2026-11-23; the task-selection models were superseded by D-008)

- Status: The layout rules remain in force; D-007's task-list model and D-005/D-006's selection/exclusivity aspects were superseded by D-008
- Context: three same-week UI waves (2026-11-18) plus the round-2/3 feedback; only the still-live rules are recorded here.
- Decision (surviving rules): every plugin surface fits the window width — the task tab's `.hams-body` is the ONLY scroll container (the console page scrolls itself: `.hams-page { height:100%; overflow-y:auto }`); `table-layout: fixed` + capped select widths so intrinsic widths cannot push tables out; `overflow-wrap: anywhere` on roots/cells/pre. Read-only text over 8 rendered lines auto-collapses (ClampText with a measured toggle; tables wrap instead). The sidebar default-opens on first sight of a session in an initialized project (untouched-host-layout gate + workspace mapping retry; blank sessions open via the localStorage layout-key poll ~1 s after creation; an explicit user close wins until another session is entered). The open-state probe requires viewport intersection AND non-hidden visibility (rc.3 hides collapsed panes while offsetWidth stays non-zero). Native selects theme via `color-scheme` + canvas colors. State colors use `light-dark()` pairs (the dark-only palette measured 2.5:1 on light cards).
- Consequences: the host's missing read faces (fork lineage, blank-session mounts) are worked around at the client; revisit when the host grows them.
