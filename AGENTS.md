# AGENTS.md — HarnessAMS (top-level repo)

> Rules for AI agents and human maintainers working in this repo. Read this file before changing anything here. This repo is the entry repo of the HarnessAMS multi-plugin system: plugin index + install guide + compatibility matrix, hosting the aggregate bundle `dsh-harnessams-suite` (in `install_suite/`); the top-level console plugin source lives in `src/index.js`. This repo keeps English-only, self-contained content (no references to files outside the repo). The single content exception is client display copy: the console UI is bilingual (zh/en) — `src/client.js` carries the zh/en dictionaries and `src/locale/*.json` the plugin-manager metadata translations; everything model-facing or server-side (docs, API error strings, check item names, the agent-diagnosis prompt, tool text) stays English-only.

- Package `dsh-harnessams` / row id `harnessams-top`; aggregate bundle `dsh-harnessams-suite` (pure patch package: its patch explicitly restates every member row — npm dependencies alone do not apply config layers).
- `engines.dsh` locks the verified DSH version (currently `0.2.2-rc.1` since 2026-11-10; an exact pin that does not cover the running host gets the plugin row DISABLED at startup — the 0.2.2 runtime enforces it even for dev-mount rows); upgrades require re-running the minimal regression before updating `docs/compatibility.md`.
- What the top-level repo does not do: no mirroring of other plugins' sources, no hosting of other plugins' patches, no overriding other plugins' config defaults in its own patch. (Exception, 2026-11-01 redistribution: the generic batch tools (renamed `bsub_*` → `batch_*` on 2026-11-09) and the `sim_*` analysis tools are OWNED here now, not mirrored — they moved out of SmartAnaSim so that plugin stays simulator-only; their worker scripts still ship with SmartAnaSim and are reached through the workspace `sim_scripts_dir`, never by copying.)
- The console plugin (in `src/`) is a three-tier client UI plus JSON APIs: tier 1 is a global page (left-sidebar "HarnessAMS" entry → keyed `main` panel) for remote projects, digital assets, and disk usage; tier 2 maps project = DSH workspace via `ctx.workspaceRegistry` (task data at `<workspace>/.harnessams/tasks.json`, sessions deliberately not modeled); tier 3 is a right-sidebar task tab, **local projects only** (2026-10-27: remote projects render a one-line note instead — they anchor the connection; the pinned reopen skips remote sessions via the `remote` flag on `/api/project`), with task strip + Overview/Dashboard/Sim-settings sub-navigation (the **Dashboard** sub-view, 2026-10-30, is an HTML-report viewer: reports register per task in tasks.json `reports[]` + `dashboard_selected`, added through the `/api/browse` one-level directory picker or a manual absolute path — anywhere on disk — and served read-only by `src/server/dashboard.js` from `/harnessams/dash/<taskId>/<reportId>/…` with each report's own directory as the boundary so relative `data/*.js` refs keep working; client = `TaskDashboard`/`AddReportDialog` in client.js: dropdown switch + key/nonce iframe hard-reload + open-in-tab; MIME is by extension on both `/dash/` and `/reports/` — the old blanket `text/html` silently killed report data scripts; the 2026-11-01 sizing/coordination pass puts the whole sidebar height chain on flex (`.hams-body` → sub-view wrapper → `.hams-dashview`/terminal root → `.hams-dashframe`/`.hams-termwrap`, no more `calc(100vh - Npx)` dead zones; ResizeObserver+FitAddon absorbs the terminal change), the iframe embeds the same-origin report compact (padding override) and scales it by the DSH font-size ratio (`embedReportFrame`), the suite's `sim_analysis(report=true, task=…)` writes generated reports straight into the store (`findTasksStore`/`registerReportIntoTask` in this package's `src/tools/shared.js` since the 2026-11-01 redistribution, store-dir-anchored walk-up, version-guarded, tmp+rename atomic — a second writer beside this sidebar), so the sidebar's full-list PUT is re-based on a fresh GET (`persist(mutator)`) and the Dashboard sub-view auto-refreshes while visible (2026-11-01 方案B: 10 s polling paused on `document.hidden` with a visibilitychange catch-up — the parent effect re-GETs `/api/tasks` while the sub-view is open, skipping persist-in-flight ticks and only touching state on an actual diff; `TaskDashboard` polls the current report's `/api/report-stat` mtime+size and reloads the iframe through the nonce on change, first sample per report = baseline only), `writeTasks` also replaces atomically; the **Terminal** sub-view, 2026-10-31, is a pooled-xterm remote terminal over dsh-remote's OWN `/dsh-remote/term/*` polling PTY routes (this plugin adds NO execution surface: it only discloses each machine's first live-session id on `/api/checks` machines[] as the binding hint — dsh-remote's `resolveRequestBinding` binds a hinted session inside the mirror to that machine's pool — and serves the vendored `@xterm/xterm 5.5.0` + fit/search addons from the whitelisted `/assets/`; fresh sessions `cd` into the machine's `remotePath` = the remote project root; machines without a live remote-project session are disabled with guidance, same precondition as the check buttons; pooled instances keep scrollback across tab/task/reload switches; browser-verified end-to-end on 2026-10-31 against node1 (resume a remote-project session → machine tab → PTY round-trip, auto-cd, snippets, search, font zoom, reopen, pooled reattach — two paint-lifecycle bugs found and fixed in that run, see CHANGELOG Fixed "Terminal sub-tab paint lifecycle"); `tests/terminal.test.mjs` pins the static contracts) and a header button re-opens it pinned on session switches. The Overview carries the local environment button plus one block per machine that has a remote project; a remote check run (`/api/checks/run?machineId=`) borrows a live session of that machine's remote project through `sessionInMirror` and parses the output into columned rows (`checks.js` parsers; `$ROOT` abbreviates the workspace-scope prefix, bjobs column layout comes from the header line). All APIs are served via `ctx.webServer.register` under `/harnessams`; failing checks offer a one-click agent diagnosis prompt. Remote connectivity is delegated entirely to dsh-remote (2026-10-26 rework removed nodes.yaml and the BatchMode ssh channel): a **remote project** is a DSH workspace inside a dsh-remote mirror (`src/server/remote.js` walks up to the nearest `.dsh-remote-meta.json`; one per machine is the recommended setup, created in one click from tier 1 by registering the machine's EXISTING mirror — mirrors are never created here: pick the remote workspace in dsh-remote first, machines without a mirror get an actionable error; the never-working ensure-mirror POST was removed 2026-10-28); checks run through the `rw_exec` tool shell with a real live session as the agent context (its cwd in the mirror binds the machine; the global active machine is never switched; coupling points for the dsh-remote pin (0.8.83 since 2026-11-10; upgraded 0.8.51→0.8.54 on 2026-10-28, 0.8.54→0.8.66 on 2026-10-31 and 0.8.66→0.8.83 on 2026-11-10, exact-pinned in the web profile) live in `src/server/checks.js`'s block comment); remote file browsing/editing is deliberately NOT duplicated — dsh-remote's own tools and web surface do it.
- dsh-remote probe gotchas (verified 2026-10-25/26/27): `tools.execute` REQUIRES `callId` + `AbortSignal` (without a signal the pipeline crashes on `signal.aborted`); `rw_machines` returns a text listing, not JSON (workspace rides on the auth line under each header line); `/dsh-remote/*` HTTP routes sit behind the DSH web auth gate, so same-origin calls forward the incoming request's cookie/authorization headers; a fabricated `{session:{header:{cwd}}}` agent does not survive the tool pipeline (session validated against the live store) — borrow a real session from the host `sessions` service (`sessionInMirror` in `src/server/machines.js`) and pass it to rw_exec as `{id, session}` (rw_exec derives the background-job owner from `exec.agent.id`; an id-less wrapper fails the call before the command runs); call rw_exec with `promoteOnTimeout:false` and an AbortSignal ~30 s above `timeoutMs`, because a borrowed agent has no job controller and a promoted command would be stranded on the remote.
- **Project settings + project self-check (2026-11-08)**: per-project settings at `<workspace>/.harnessams/project_settings.json` (`src/server/settings.js`, `GET`/`PUT /api/project-settings`) — `run_mode` local/remote, `machine_id`, `remote_dir` (relative to the machine's remotePath or absolute), `scheduler` lsf/direct, `simulator` spectre/none, `compute_script_local`/`compute_script_remote` python/js. The Overview renders them as a two-row table (row 1 = live settings as dropdown cells that PUT on every change, row 2 = the setting's self-check verdict aggregated from server-tagged `settingColumn` steps; columns cascade off mode/simulator; a working-directory line above the table always shows `local` or the bound remote dir — browse-picked through the machine's LOCAL mirror via `/api/browse` and converted back to a remote path). The one-click **project self-check** (`src/server/selfcheck.js`, `POST /api/selfcheck` starts a background run, `GET /api/selfcheck?id=` polls; server reads the settings itself — single source of truth) walks the whole pipeline under the current settings with NO LLM in the flow: `simulator=spectre` = ideal RC LPF/HPF tb (3×3 grid, `src/selfcheck/script/analysis/gen_selfcheck_rc.py`, no PDK) through the SmartAnaSim tool shell (assemble → run_sweep → parse → verify locally; batch submit/poll → remote parse+verify → fetch + cross-check remotely — an LSF failure is diagnosed IMMEDIATELY and retried once with `scheduler=direct`, verdict `ok-via-fallback`); `simulator=none` = no simulation, the bundled analytic golden dataset (`src/selfcheck/golden/`, 36 psfascii files, regenerated byte-identically by `tests/golden_gen.py`) replays parse + compute locally or upload → remote compute → download + cross-check. Verification is POINTWISE (every frequency sample vs the analytic RC response, 1% tolerance — NOT a -3dB extraction) with one JSON contract implemented twice: `src/scripts/selfcheck/selfcheck_verify.py` (local spawn / remote python) and `.mjs` (local = in-process import, remote = `node` on the remote host, `remote_node` workspace key). Verdicts are artifact-driven (sweep_progress.json / psf_index.json / .batch_job.json) because ctx.tools.execute's serialization of model-tool results is a launch-class TODO; failures auto-start diagnosis sessions (the scheduler cluster at once, the rest at run end — `buildSelfcheckPrompt` reuses diagnose.js's caps). Guard rails: local projects only, one running self-check per session (409), id-addressed runs only (the global restore-latest surface was removed 2026-11-09 — it bled verdicts across projects), 30-min budget, every rw_exec command bash -n testable.
- The client half `src/client.js` is a single-file classic script registered on `window.__ModuleLoader__` (React via the loader's synchronous `require`) — combo-loaded classic scripts cannot `import` sibling modules, so everything browser-side lives in that one file. Keep it that way (no build chain); the `dsh.client` declaration in `package.json` (`inject` + `platform: web`) and `exports["./client"]` must match the loader contract. Wrap every console section in the error boundary so one failure never blanks the rest.
- Client copy is locale-owned (verified against the installed DSH 0.2.1-rc.2, 2026-10-25): all UI strings live in the `L = { zh, en }` dictionary with stable keys and `{param}` interpolation; `wireLocale(ctx)` (called from `apply()`, which requires `exports.inject = ['slots', 'locale']`) registers the dictionary into the DSH locale service (`locale.register`/`locale.bind` — the language follows the client's Language setting) and falls back to the browser language, then English, when the service is absent. zh and en must keep identical key sets; a missing key renders the English text, never the raw key. `exports.meta` localization rides the same contract from the host side: `src/locale/en.json` + `zh.json` carry `{ "meta": { "title", "description" } }` (DSH `readPluginMeta` reads `<pkg>/locale/en.json` through the `exports` map; package.json `name`/`description` stay the en fallback). Do not translate server strings or the diagnosis prompt.
- Safety by default: destructive operations move paths to the trash folder (`safe_trash`, the JS module `src/trash.js` since 2026-11-09 — fenced restore/purge; it replaced the `common_trash.py` python whose `--restore/--purge` accepted `../` traversal); bestPoints persistence was removed 2026-11-01.
- Custom web routes are not token-gated by the DSH web server: serve only management UI and static reports on them; never expose credentials or remote-execution surfaces without adding an auth layer.
- Workspace convention (runtime, outside any repo): a `harnessams.json` at the workspace root provides fixed paths (`pdk_lib`, `trash_dir`); relative values resolve against the config file's directory; the plugin locates it by walking upward from the package and from cwd (bare form, or inside `harnessams-workspace/`).
- Repo layout: console plugin package in `src/` (host-half entry `src/index.js` assembling `src/server/` modules and registering the model tools in a second `ctx.effect`; browser half `src/client.js`, plain JS, no build chain; **model tools (2026-11-01 redistribution)**: `src/tools/{batch,sim_analysis}.js` + `src/{tool,py,batch,remote}.js` register 6 tools — `batch_submit`/`batch_poll`/`batch_fetch` (generic remote batch/LSF, renamed from `bsub_*` on 2026-11-09 with the scheduler value `none` → `direct`; module files renamed to match on 2026-11-10 — job record `.batch_job.json`, fetch archive `.batch_fetch.tgz`; the worker upload tree / worker lookup root is the workspace `sim_scripts_dir`, normally the SmartAnaSim package's `scripts/`; `HARNESSAMS_SIM_SCRIPTS_DIR` overrides discovery; the batch domain contract — borrowed `{ id, session }` live session, `promoteOnTimeout: false`, `template.scs` convention, remote write fence, `bjobs` `No job found` = completed, `fetch_<job>.tgz` kept — moved verbatim from SmartAnaSim) and `sim_analysis`/`sim_progress`/`safe_trash` (sim_analysis = collect + optional `report=true` dashboard rendering with `task=` injection; sim_progress is the LOCAL progress-file window — during a remote batch poll `batch_poll` instead, which also sees the LSF queue; simulator-agnostic analysis over the `point_meta.json`/`sweep_progress.json` data contract; safe_trash's definition lives in `src/trash.js` (`safeTrashTool()`; the JS rewrite is 2026-11-09 — fenced restore/purge, replaced `common_trash.py`; the tool def moved there 2026-11-10); the collect/report pipeline is pure JS inside `sim_analysis.js` since 2026-11-10 (ported from `src/scripts/common/*.py`, which stay there only as `_dont_use_*` reference copies, excluded from the tarball) — `src/py.js`'s `runPython` now only serves the self-check (`SCRIPTS_DIR` still points inside this package; unlike SmartAnaSim the npm package root IS `src/` here); self-check assets: `src/scripts/selfcheck/` (the `selfcheck_verify.py`/`.mjs` compute twins) and `src/selfcheck/` (the RC gen script + the golden dataset); `sim_analysis(report=true, task=…)` injects reports into `.harnessams/tasks.json` via the store-mirrored guarded writer in `src/tools/sim_analysis.js` (a same-package second writer beside `server/project.js`); the package also ships `src/assets/` — `PUBLISH.md` holds the must-contain / must-not-contain tarball checks), aggregate bundle in `install_suite/`, unit tests in `tests/` (bare `node --test` from the repo root; a directory argument fails on Node 24).
- Language rule (2026-11-10, decision D-004 in `docs/decisions.md`): everything inside the plugin is JS single-implementation by default; Python is confined to three scenario families — remote-runnable sweep workers (e.g. `spectre_sweep_worker.py`, shipped by SmartAnaSim), s-parameter numeric computing (e.g. `snp_extract.py`), and per-project user-authored assembly scripts (e.g. `gen_selfcheck_rc.py`) — with no new Python families beyond these.
- `src/assets/` holds the **master** `plotly.min.js` for the whole HarnessAMSproject tree (plus its THIRD_PARTY_NOTICES). Never add a second copy anywhere under the project; it ships inside the `dsh-harnessams` tarball and is served in-app at `/harnessams/assets/plotly.min.js`. Report generators do not reference it directly — they seed the workspace-level copy `<workspace_root>/assets/plotly.min.js` from it (discovered by walking up from their own location, via the workspace `plotly_asset` config field, or from a sibling `dsh-harnessams` install under `node_modules/`) and embed a workspace-relative `src`; the CDN is the last-resort fallback. Decision record: `docs/decisions.md` (D-001).
- `LocalDesignExample/` was removed on 2026-11-02 (it bundled the retired ngspice channel: the portable binary, the sky130 spice closure and the pipeline-script mirrors). The pre-removal state lives in this repo's `ngspice` branch — do not reintroduce vendored simulator binaries or PDK model files into the repo.
- Script-sync check (`src/server/checks.js`): it walks the configured local `sim_scripts_dir` recursively (relative POSIX keys, ≤50 `.py`, skips `__pycache__`) and compares against the remote scripts root — `remote_scripts_dir` when the workspace `harnessams.json` sets it (a REMOTE absolute path; never resolve it against a local base), else the remote workspace root. The remote command uses `md5sum` plus a bounded `find`; keep it in sync with the pipeline's nested layout.
- sky130 closure fact: `combined_models/` alone is NOT a working copy — `corners/*.spice` reference `cells/` models through two levels of relative includes, so the minimal closure is combined_models plus those cells files; copying only combined_models fails with `Could not find include file`.
- Self-contained HTML pages (generated reports) have no bundler safety net: one JavaScript syntax error silently blanks the whole page. Keep the per-section try/catch isolation and test-render after edits. The client half has the same discipline via error boundaries; after editing `client.js`, run `node --check src/client.js` and reload a dev-mount page before considering the edit done.
- Commits: local commits are at the agent's discretion (no per-commit approval needed); **pushing is always manual** — automated flows must never push. Messages in English (`<verb> <scope>: <summary>`), one topic per commit.
