# AGENTS.md — HarnessAMS (top-level repo)

> Rules for AI agents and human maintainers working in this repo. Read this file before changing anything here. This repo is the entry repo of the HarnessAMS multi-plugin system: plugin index + install guide + compatibility matrix, hosting the aggregate bundle `dsh-harnessams-suite` (in `install_suite/`); the top-level console plugin source lives in `src/index.js`. This repo keeps English-only, self-contained content (no references to files outside the repo). The single content exception is client display copy, enforced by the pre-commit content gate (see the content-gates bullet below): the console UI is bilingual (zh/en) — `src/client/client.js` carries the zh/en dictionaries and `src/locale/*.json` the plugin-manager metadata translations; everything model-facing or server-side (docs, API error strings, check item names, the agent-diagnosis prompt, tool text) stays English-only.

- Package `dsh-harnessams` / row id `harnessams-top`; aggregate bundle `dsh-harnessams-suite` (pure patch package: its patch explicitly restates every member row — npm dependencies alone do not apply config layers).
- `engines.dsh` locks the verified DSH version (currently `0.2.2-rc.5` since 2026-11-21 — the rc.5 re-pin wave; an exact pin that does not cover the running host gets the plugin row DISABLED at startup — the 0.2.2 runtime enforces it even for dev-mount rows); upgrades require re-running the minimal regression before updating `docs/compatibility.md`.
- What the top-level repo does not do: no mirroring of other plugins' sources, no hosting of other plugins' patches, no overriding other plugins' config defaults in its own patch. **Suite division (D-001, 2026-11-23)**: this repo owns the managed scan methodology — the batch channel (`batch_submit` with its local/ssh/lsf schedulers (semantics set by the project cluster_env working environment, D-002), `batch_poll` monitoring with the terminal auto-fetch) plus `gen_sweep_report`/`register_report`/`safe_trash`/`harnessams_selfcheck`; SmartAnaSim is a PURE standalone tool set (spectre assembly + checks + snp_* + its directly runnable worker/parser scripts + its own smart-spectre configuration skill) and references no other plugin's tools anywhere in its surface. The worker scripts still ship with SmartAnaSim, and each project's worker-scripts root resolves to that package's `scripts/` tree at its install location (D-033: nothing is staged at store creation; a legacy project-local `<project>/.harnessams/scripts` root is healed copy-if-missing at self-check start — `src/core/scriptStage.js`; the self-check's `gen_selfcheck_rc.py` is never staged — it runs from this package's install location, and the project `script/` folder is retired since 2026-11-25). Skills here: `src/skills.js` scans `src/skills/<name>/SKILL.md` and registers them into the host `ctx.skills` catalog (`batch-sweep` — the generic scan methodology, renamed from smart-spectre 2026-11-23 — plus `cluster-setup` — the once-per-cluster toolchain bootstrap: harvest the login startup chain, verify the candidates as absolute paths, pin them in the project settings (D-016), added 2026-11-24 — plus `dca-cell-design` and `dca-cascade-analysis`); each package carries the skill for its OWN surface (D-001 supersedes D-001's single-homing rule).

The exec funnel (`execRemote` in `src/channel/remote.js`) wraps every command in a remote `timeout -s KILL`, treats exit 137 as the deadline, annotates channel-open failures with a suspected-MaxSessions hint, and sizes the outer AbortSignal for dsh-ssh's ≤3 broken-connection replays.
- dsh-ssh consumption contract (0.4.18, re-verified against the installed package's `src/tools.ts` on 2026-11-14): only `ssh_list`/`ssh_exec`/`ssh_upload`/`ssh_download` are consumed, all through the `callTool` batch-contract funnel in `src/channel/remote.js`; results are STRUCTURED VALUES on `result.value` (`ToolExecutionSuccess.value`) — `ssh_list` → `{hosts:[…]}` (secret-free rows), `ssh_exec` → `{success, exitCode|null, timedOut, stdout, stderr, durationMs, error?}`, transfers → `{ok, …bytes/files, error?}` — and connect/channel failures arrive as VALUES (success:false / ok:false with `error`), not throws; `tools.execute` still REQUIRES the batch input shape with a signal (without one the pipeline crashes on `signal.aborted`; the 0.2.1 single-call shape fails on `calls.map` wrapped as an opaque "Tool batch execution failed" — the real cause rides `e.cause`, unwrapped by `errDetail`). Known pitfalls the funnel compensates: a broken connection replays a non-idempotent exec up to 3 times (marker+flock guards in `buildSubmitCommand`/`buildSshCommand`; an `overwrite: true` submit clears stale markers and tags the fresh ones so a finished batch re-runs while replays still short-circuit), `ssh_download` is single-file only (a terminal batch_poll pulls the light result files per file — no archive), the upload TOOL surface has no `recursive` (uploads are per-file), and telemetry is on by default (opt out via localStorage `dsh-web-ui-telemetry-opt-out=1` or DNT).
- **Project settings + project self-check (D-004, 2026-11-19; originally 2026-11-08)**: per-project settings live in `<workspace>/.harnessams/workspace_config.json` `settings` — `cluster_env` in-cluster/out-of-cluster (the working-environment dichotomy, D-002; switched by the overview toggle behind a confirm dialog), `run_mode` local/remote, `machine_id`, `remote_root` (REQUIRED in remote mode; fences `remote_dir`), `remote_dir` (relative to the project's remote root, or absolute), `scheduler` lsf/ssh, `simulator` spectre/none, `compute_script_local`/`compute_script_remote` python/js, `remote_python`/`remote_spectre_cmd` (the cluster toolchain pins, D-016: absolute paths to the worker interpreter and to the spectre executable, null = the bare defaults; deliberately not a settings-table row — the agent pins them through the tool's `settings` argument and the AGENTS.md yaml is where they are kept) — beside a `workspace` section (`sim_scripts_dir`/`trash_dir` default-filled at store creation; `plotly_url`/`plotly_asset` are known-but-optional — present values survive every rewrite, never default-filled, the `plotly_url` declaration appearing only after the first successful on-open seed, D-021 2026-11-26 on-demand ruling; `HARNESSAMS_SIM_SCRIPTS_DIR` still overrides discovery). Read face: `GET /api/project-settings` (table init only — the PUT is retired); write face: exactly ONE — the `harnessams_selfcheck` tool's optional `settings` object (full, or partial — merged key by key over the stored settings; validated, then written before the action runs), reached by the UI through `POST /api/tool`. The Overview renders a STAGED table (edits red-marked "unsaved" until the confirm or any action button commits; columns cascade off mode/simulator; a working-directory line above the table always shows `local` or the bound remote dir — picked through `GET /api/remote-browse`, whose default root is `settings.remote_root`; missing root → 409). The one-click **project self-check** (`src/core/selfcheck.js`, started via the tool's `run` action, polled via `status` by run_id with project fencing on both the memory hit and the disk fallback; server reads the settings itself — single source of truth) walks the whole pipeline under the current settings with NO LLM in the flow: `simulator=spectre` = ideal RC LPF/HPF tb (3×3 grid, `src/selfcheck/script/analysis/gen_selfcheck_rc.py`, no PDK) through the tool shell (the package's `gen_selfcheck_rc.py` runs directly from its install location, cwd = the project root — nothing is staged into the project, the `script/` folder is retired → batch_submit(scheduler=local, the SmartAnaSim netlist pre-check built in, D-020) → batch_poll → the standalone parser run directly → pointwise verify, locally; batch submit/poll → remote parse+verify → per-file result download + cross-check remotely — an LSF failure is diagnosed IMMEDIATELY and retried once with `scheduler=ssh` when a machine is configured — an in-cluster LSF-only project has no fallback — verdict `ok-via-fallback`); `simulator=none` = no simulation, the bundled analytic golden dataset (`src/selfcheck/golden/`, 36 psfascii files, regenerated byte-identically by `tests/golden_gen.py`) replays parser + compute locally or upload → remote compute → download + cross-check (data processing is script-face since 2026-11-23 — the parse step runs `spectre_psf_parse.py` from the project's `sim_scripts_dir` directly; C1 gates `spectre_pre_check`+`batch_submit`+`batch_poll`, or the parser's existence in simulator=none). Verification is POINTWISE (every frequency sample vs the analytic RC response, 1% tolerance — NOT a -3dB extraction) with one JSON contract implemented twice: `src/scripts/selfcheck/selfcheck_verify.py` (local spawn / remote python) and `.mjs` (local = in-process import, remote = `node` on the remote host). Verdicts are artifact-driven (sweep_progress.json / psf_index.json / .batch_job.json). Runs land in `<project>/.harnessams/selfcheck/<runId>/` — a CLEAN run's artifacts are deleted at finalize (regenerable runtime products), a diagnosed/failed run keeps its evidence for the diagnosis sessions, and the NEXT run's start cleans historical evidence (`selfcheck_run.json` always survives); finalize also re-syncs AGENTS.md unconditionally, so `last_selfcheck_*` can never go stale (the old family-root/project-dir path mismatch that kept the field permanently null is closed). - The client half `src/client/client.js` is a single-file classic script registered on `window.__ModuleLoader__` (React via the loader's synchronous `require`) — combo-loaded classic scripts cannot `import` sibling modules, so everything browser-side lives in that one file. Keep it that way (no build chain); the `dsh.client` declaration in `package.json` (`inject` + `platform: web`) and `exports["./client"]` must match the loader contract. Wrap every console section in the error boundary so one failure never blanks the rest.
- Client copy is locale-owned (verified against the installed DSH 0.2.1-rc.2, 2026-10-25): all UI strings live in the `L = { zh, en }` dictionary with stable keys and `{param}` interpolation; `wireLocale(ctx)` (called from `apply()`, which requires `exports.inject = ['slots', 'locale']`) registers the dictionary into the DSH locale service (`locale.register`/`locale.bind` — the language follows the client's Language setting) and falls back to the browser language, then English, when the service is absent. zh and en must keep identical key sets; a missing key renders the English text, never the raw key. `exports.meta` localization rides the same contract from the host side: `src/locale/en.json` + `zh.json` carry `{ "meta": { "title", "description" } }` (DSH `readPluginMeta` reads `<pkg>/locale/en.json` through the `exports` map; package.json `name`/`description` stay the en fallback). Do not translate server strings or the diagnosis prompt.
- Controlled controls + the rebased session persist: the session panel's `persistConfig` applies its mutator only after an await (the rebase GET), and a controlled `<select>` snaps back to its rendered value the moment the change event ends. A handler must therefore read the control's value SYNCHRONOUSLY (`captureValue`) and hand it on: reading `e.target.value` inside the mutator returns the OLD value (the dashboard dropdown could not switch away from the newest report).
- Safety by default: destructive operations move paths to the trash folder (`safe_trash`, the JS module `src/tools/trash.js` since 2026-11-09 — fenced restore/purge; it replaced the `common_trash.py` python whose `--restore/--purge` accepted `../` traversal); bestPoints persistence was removed 2026-11-01.
- Custom web routes are not token-gated by the DSH web server: serve only management UI and static reports on them; never expose credentials or remote-execution surfaces without adding an auth layer.
- Workspace convention (runtime, outside any repo; D-004): each project owns a single config at `<project>/.harnessams/workspace_config.json` — `workspace: {sim_scripts_dir, plotly_asset, trash_dir}` (laid down once with resolved defaults at store creation) + `settings` (incl. `remote_root`, a REMOTE absolute path — never resolved against a local base).
