# AGENTS.md — HarnessAMS (top-level repo)

> Rules for AI agents and human maintainers working in this repo. Read this file before changing anything here. This repo is the entry repo of the HarnessAMS multi-plugin system: plugin index + install guide + compatibility matrix, hosting the aggregate bundle `dsh-harnessams-suite` (in `install_suite/`); the top-level console plugin source lives in `src/index.js`. This repo keeps English-only, self-contained content (no references to files outside the repo). The single content exception is client display copy: the console UI is bilingual (zh/en) — `src/client.js` carries the zh/en dictionaries and `src/locale/*.json` the plugin-manager metadata translations; everything model-facing or server-side (docs, API error strings, check item names, the agent-diagnosis prompt, tool text) stays English-only.

- Package `dsh-harnessams` / row id `harnessams-top`; aggregate bundle `dsh-harnessams-suite` (pure patch package: its patch explicitly restates every member row — npm dependencies alone do not apply config layers).
- `engines.dsh` locks the verified DSH version (currently `0.2.2-rc.3` since 2026-11-14 — the dsh-ssh migration wave; an exact pin that does not cover the running host gets the plugin row DISABLED at startup — the 0.2.2 runtime enforces it even for dev-mount rows); upgrades require re-running the minimal regression before updating `docs/compatibility.md`.
- What the top-level repo does not do: no mirroring of other plugins' sources, no hosting of other plugins' patches, no overriding other plugins' config defaults in its own patch. (Exception, 2026-11-01 redistribution: the generic batch tools (renamed `bsub_*` → `batch_*` on 2026-11-09) and the `sim_*` analysis tools are OWNED here now, not mirrored — they moved out of SmartAnaSim so that plugin stays simulator-only; their worker scripts still ship with SmartAnaSim and are reached through the workspace `sim_scripts_dir`, never by copying.) The boundary extends to skills (D-013 in `docs/decisions.md`): bundled skills and workflow/orchestration knowledge are OWNED here — `src/skills.js` scans `src/skills/<name>/SKILL.md` and registers them into the host `ctx.skills` catalog (`smart-spectre` + `dca-design` since D-011) — and SmartAnaSim carries NO bundled skills, none now and none later: it ships simulator tools only.
- The console plugin (in `src/`) is a three-tier client UI plus JSON APIs: tier 1 is a global page (left-sidebar "HarnessAMS" entry → keyed `main` panel) for machines (a read-only projection of the dsh-ssh host registry — remote roots are per-project settings since D-009, not machine data) and digital assets (the disk-usage block and the remote-project section are retired — server/disk.js died with D-009, the dsh-remote mirror model with the 2026-11-14 retirement); tier 2 maps project = DSH workspace via `ctx.workspaceRegistry` — each project's state is its own `.harnessams/` store (`workspace_config.json` + `sessions.json` v2; tasks are retired since D-008, every session is a work unit, a forked session deep-copies the last-active session's entry — deliberately branch-point-independent — and `server/forkdetect.js` detects forks from the child log's `session/end-seed` + `inherited:true` marker); tier 3 is the right-sidebar tab whose first-level strip is exactly TWO entries — project overview + this session (no creation button, no task names; D-008), the session panel keeping Dashboard/Check-params sub-views (the Sim-settings placeholder is deleted; the remote-project model — workspaces inside dsh-remote mirrors, no sidebar there — was removed with the dsh-remote retirement, 2026-11-14) (the **Dashboard** sub-view, 2026-10-30, is an HTML-report viewer: since D-008 reports register per SESSION in sessions.json v2 `reports[]` + `dashboard_selected` — `gen-sweep-report` targets the calling session via `exec.agent.id` (≡ SessionId; the old `task=` parameter is gone; absent identity = visible register_error), added through the `/api/browse` one-level directory picker or a manual absolute path — anywhere on disk — and served read-only by `src/server/dashboard.js` from `/harnessams/dash/<sessionId>/<reportId>/…` with each report's own directory as the boundary so relative `SimResults/*.js` refs keep working; client = `TaskDashboard`/`AddReportDialog` in client.js: dropdown switch + key/nonce iframe hard-reload + open-in-tab; MIME is by extension on both `/dash/` and `/reports/` — the old blanket `text/html` silently killed report data scripts; the 2026-11-01 sizing/coordination pass puts the whole sidebar height chain on flex (`.hams-body` → sub-view wrapper → `.hams-dashview`/terminal root → `.hams-dashframe`/`.hams-termwrap`, no more `calc(100vh - Npx)` dead zones; ResizeObserver+FitAddon absorbs the terminal change), the iframe embeds the same-origin report compact (padding override) and scales it by the DSH font-size ratio (`embedReportFrame`; the sub-view set was Dashboard/Check params/Terminal/Sim settings until the 2026-11-14 retirement removed the Terminal sub-view — the interactive shell is dsh-ssh's own terminal panel now), the suite's `gen-sweep-report` writes generated reports straight into the calling session's store entry (store-dir-anchored walk-up, version-guarded, tmp+rename atomic — a second writer beside this sidebar), the sidebar merge-writes single sessions through `PUT /api/session-config`, and the Dashboard sub-view auto-refreshes while visible (10 s polling paused on `document.hidden` with a visibilitychange catch-up; `TaskDashboard` polls the current report's `/api/report-stat?sessionId=` mtime+size and reloads the iframe through the nonce on change, first sample per report = baseline only). The project overview carries the project-settings + self-check block (the sole entry since the health-check panel retired 2026-11-18 — the per-machine check buttons and `/api/checks/run` are gone): a STAGED settings table (edits red-marked "unsaved" until the confirm button or any action button commits them through `POST /api/tool`) and four buttons — Save to AGENTS.md / One-click self-check / List local environment / Check all & save — all funneling into the `harnessams_selfcheck` tool runner (`POST /api/tool {sessionId, action, settings?}`; every action commits pending table edits first, so UI = json = AGENTS.md can never diverge; the optional `settings` object is the single config write face for conversational agents too). All APIs are served via `ctx.webServer.register` under `/harnessams`; self-check failures auto-start diagnosis sessions through the private session-controller channel (`server/diagnose.js`). Remote connectivity is delegated entirely to **@linxin666/dsh-ssh** (0.4.18 exact-pinned since 2026-11-14, replacing dsh-remote 0.8.94 which was retired the same day — the retired mirror/remote-project/borrowed-session model's history lives in the root repo's dependency-check doc §2.6 archive): machines are aliases in dsh-ssh's host registry (`~/.dsh/dsh-ssh.json`, GUI-managed) and each project's remote root is its own `settings.remote_root` in `.harnessams/workspace_config.json` (D-009; the family `harnessams.json` `remote_machines` map, `readRemoteMachines`, and the `HARNESSAMS_REMOTE_MACHINES` test seam are all retired — `listMachines` is a pure registry projection with no root field; `batch_submit` requires `remote_root` and records it in `.batch_job.json` for poll/fetch to inherit); the interactive SSH terminal is dsh-ssh's own panel — neither is duplicated here. The exec funnel (`execRemote` in `src/remote.js`) wraps every command in a remote `timeout -s KILL`, treats exit 137 as the deadline, annotates channel-open failures with a suspected-MaxSessions hint, and sizes the outer AbortSignal for dsh-ssh's ≤3 broken-connection replays.
- dsh-ssh consumption contract (0.4.18, re-verified against the installed package's `src/tools.ts` on 2026-11-14): only `ssh_list`/`ssh_exec`/`ssh_upload`/`ssh_download` are consumed, all through the `callTool` batch-contract funnel in `src/remote.js`; results are STRUCTURED VALUES on `result.value` (`ToolExecutionSuccess.value`) — `ssh_list` → `{hosts:[…]}` (secret-free rows), `ssh_exec` → `{success, exitCode|null, timedOut, stdout, stderr, durationMs, error?}`, transfers → `{ok, …bytes/files, error?}` — and connect/channel failures arrive as VALUES (success:false / ok:false with `error`), not throws; `tools.execute` still REQUIRES the batch input shape with a signal (without one the pipeline crashes on `signal.aborted`; the 0.2.1 single-call shape fails on `calls.map` wrapped as an opaque "Tool batch execution failed" — the real cause rides `e.cause`, unwrapped by `errDetail`). Known pitfalls the funnel compensates: a broken connection replays a non-idempotent exec up to 3 times (marker+flock guards in `buildSubmitCommand`/`buildDirectCommand`), `ssh_download` is single-file only (batch_fetch tars remotely first), the upload TOOL surface has no `recursive` (uploads are per-file), and telemetry is on by default (opt out via localStorage `dsh-web-ui-telemetry-opt-out=1` or DNT).
- **Project settings + project self-check (D-009, 2026-11-19; originally 2026-11-08)**: per-project settings live in `<workspace>/.harnessams/workspace_config.json` `settings` — `run_mode` local/remote, `machine_id`, `remote_root` (REQUIRED in remote mode; fences `remote_dir`), `remote_dir` (relative to the project's remote root, or absolute), `scheduler` lsf/direct, `simulator` spectre/none, `compute_script_local`/`compute_script_remote` python/js — beside a `workspace` section (`sim_scripts_dir`/`plotly_asset`/`trash_dir`, default-filled at store creation; `HARNESSAMS_SIM_SCRIPTS_DIR` still overrides discovery). Read face: `GET /api/project-settings` (table init only — the PUT is retired); write face: exactly ONE — the `harnessams_selfcheck` tool's optional `settings` object (validated, then written before the action runs), reached by the UI through `POST /api/tool`. The Overview renders a STAGED table (edits red-marked "unsaved" until the confirm or any action button commits; columns cascade off mode/simulator; a working-directory line above the table always shows `local` or the bound remote dir — picked through `GET /api/remote-browse`, whose default root is `settings.remote_root`; missing root → 409). The one-click **project self-check** (`src/server/selfcheck.js`, started via the tool's `run` action, polled via `status` by run_id with project fencing on both the memory hit and the disk fallback; server reads the settings itself — single source of truth) walks the whole pipeline under the current settings with NO LLM in the flow: `simulator=spectre` = ideal RC LPF/HPF tb (3×3 grid, `src/selfcheck/script/analysis/gen_selfcheck_rc.py`, no PDK) through the SmartAnaSim tool shell (assemble → run_sweep → parse → verify locally; batch submit/poll → remote parse+verify → fetch + cross-check remotely — an LSF failure is diagnosed IMMEDIATELY and retried once with `scheduler=direct`, verdict `ok-via-fallback`); `simulator=none` = no simulation, the bundled analytic golden dataset (`src/selfcheck/golden/`, 36 psfascii files, regenerated byte-identically by `tests/golden_gen.py`) replays parse + compute locally or upload → remote compute → download + cross-check. Verification is POINTWISE (every frequency sample vs the analytic RC response, 1% tolerance — NOT a -3dB extraction) with one JSON contract implemented twice: `src/scripts/selfcheck/selfcheck_verify.py` (local spawn / remote python) and `.mjs` (local = in-process import, remote = `node` on the remote host). Verdicts are artifact-driven (sweep_progress.json / psf_index.json / .batch_job.json). Runs land in `<project>/.harnessams/selfcheck/<runId>/` — a CLEAN run's artifacts are deleted at finalize (regenerable runtime products), a diagnosed/failed run keeps its evidence for the diagnosis sessions, and the NEXT run's start cleans historical evidence (`selfcheck_run.json` always survives); finalize also re-syncs AGENTS.md unconditionally, so `last_selfcheck_*` can never go stale (the old family-root/project-dir path mismatch that kept the field permanently null is closed). Failures auto-start diagnosis sessions (the scheduler cluster at once, the rest at run end — `buildSelfcheckPrompt` reuses diagnose.js's caps and cites `settings.remote_root`). Guard rails: local projects only, one running self-check per session (409), id-addressed runs only (the global restore-latest surface was removed 2026-11-09 — it bled verdicts across projects), 30-min budget, every ssh_exec command bash -n testable (the funnel's `timeout -s KILL` wrapper included).
- The client half `src/client.js` is a single-file classic script registered on `window.__ModuleLoader__` (React via the loader's synchronous `require`) — combo-loaded classic scripts cannot `import` sibling modules, so everything browser-side lives in that one file. Keep it that way (no build chain); the `dsh.client` declaration in `package.json` (`inject` + `platform: web`) and `exports["./client"]` must match the loader contract. Wrap every console section in the error boundary so one failure never blanks the rest.
- Client copy is locale-owned (verified against the installed DSH 0.2.1-rc.2, 2026-10-25): all UI strings live in the `L = { zh, en }` dictionary with stable keys and `{param}` interpolation; `wireLocale(ctx)` (called from `apply()`, which requires `exports.inject = ['slots', 'locale']`) registers the dictionary into the DSH locale service (`locale.register`/`locale.bind` — the language follows the client's Language setting) and falls back to the browser language, then English, when the service is absent. zh and en must keep identical key sets; a missing key renders the English text, never the raw key. `exports.meta` localization rides the same contract from the host side: `src/locale/en.json` + `zh.json` carry `{ "meta": { "title", "description" } }` (DSH `readPluginMeta` reads `<pkg>/locale/en.json` through the `exports` map; package.json `name`/`description` stay the en fallback). Do not translate server strings or the diagnosis prompt.
- Safety by default: destructive operations move paths to the trash folder (`safe_trash`, the JS module `src/trash.js` since 2026-11-09 — fenced restore/purge; it replaced the `common_trash.py` python whose `--restore/--purge` accepted `../` traversal); bestPoints persistence was removed 2026-11-01.
- Custom web routes are not token-gated by the DSH web server: serve only management UI and static reports on them; never expose credentials or remote-execution surfaces without adding an auth layer.
- Workspace convention (runtime, outside any repo; D-009): each project owns a single config at `<project>/.harnessams/workspace_config.json` — `workspace: {sim_scripts_dir, plotly_asset, trash_dir}` (laid down once with resolved defaults at store creation) + `settings` (incl. `remote_root`, a REMOTE absolute path — never resolved against a local base). Relative values resolve against the config file's directory; the store is located by walking up from the run directory / cwd for a `.harnessams` directory. The family root `harnessams.json` is retired (its discovery walker and the `pdk_lib`/`workspace_root`/`remote_node`/`remote_scripts_dir`/`remote_machines` keys included); existing state was archived with an `_old` suffix, never migrated.

- Language rule (2026-11-10, decision D-004 in `docs/decisions.md`): everything inside the plugin is JS single-implementation by default; Python is confined to three scenario families — remote-runnable sweep workers (e.g. `spectre_sweep_worker.py`, shipped by SmartAnaSim), s-parameter numeric computing (e.g. `snp_extract.py`), and per-project user-authored assembly scripts (e.g. `gen_selfcheck_rc.py`) — with no new Python families beyond these.

- Fixture hygiene (2026-11-12): tests and docs never carry real cluster account tokens, private-net IPs, local drive paths or the dev machine name — use the neutral placeholders (`op`, `test_user`, documentation-range `192.0.2.x` IPs, `D:/proj/...`); the repo's whole history was scrubbed to these placeholders on 2026-11-12 (commit hashes changed, content otherwise identical). - Commits: local commits are at the agent's discretion (no per-commit approval needed); **pushing is always manual** — automated flows must never push. Messages in English (`<verb> <scope>: <summary>`), one topic per commit.
