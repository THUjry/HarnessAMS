# AGENTS.md — HarnessAMS (top-level repo)

> Rules for AI agents and human maintainers working in this repo. Read this file before changing anything here. This repo is the entry repo of the HarnessAMS multi-plugin system: plugin index + install guide + compatibility matrix, hosting the aggregate bundle `dsh-harnessams-suite` (in `install_suite/`) and the bundled `LocalDesignExample` environment; the top-level console plugin source lives in `src/index.js`. This repo keeps English-only, self-contained content (no references to files outside the repo). The single content exception is client display copy: the console UI is bilingual (zh/en) — `src/client.js` carries the zh/en dictionaries and `src/locale/*.json` the plugin-manager metadata translations; everything model-facing or server-side (docs, API error strings, check item names, the agent-diagnosis prompt, tool text) stays English-only.

- Package `dsh-harnessams` / row id `harnessams-top`; aggregate bundle `dsh-harnessams-suite` (pure patch package: its patch explicitly restates every member row — npm dependencies alone do not apply config layers).
- `engines.dsh` locks the verified DSH version; upgrades require re-running the minimal regression before updating `docs/compatibility.md`.
- What the top-level repo does not do: no mirroring of other plugins' sources, no hosting of other plugins' patches, no overriding other plugins' config defaults in its own patch.
- The console plugin (in `src/`) is a three-tier client UI plus JSON APIs: tier 1 is a global page (left-sidebar "HarnessAMS" entry → keyed `main` panel) for remote projects, digital assets, and disk usage; tier 2 maps project = DSH workspace via `ctx.workspaceRegistry` (task data at `<workspace>/.harnessams/tasks.json`, sessions deliberately not modeled); tier 3 is a right-sidebar task tab, **local projects only** (2026-10-27: remote projects render a one-line note instead — they anchor the connection; the pinned reopen skips remote sessions via the `remote` flag on `/api/project`), with task strip + Overview/Dashboard/Sim-settings sub-navigation (the **Dashboard** sub-view, 2026-10-30, is an HTML-report viewer: reports register per task in tasks.json `reports[]` + `dashboard_selected`, added through the `/api/browse` one-level directory picker or a manual absolute path — anywhere on disk — and served read-only by `src/server/dashboard.js` from `/harnessams/dash/<taskId>/<reportId>/…` with each report's own directory as the boundary so relative `data/*.js` refs keep working; client = `TaskDashboard`/`AddReportDialog` in client.js: dropdown switch + key/nonce iframe hard-reload + open-in-tab; MIME is by extension on both `/dash/` and `/reports/` — the old blanket `text/html` silently killed report data scripts; the **Terminal** sub-view, 2026-10-31, is a pooled-xterm remote terminal over dsh-remote's OWN `/dsh-remote/term/*` polling PTY routes (this plugin adds NO execution surface: it only discloses each machine's first live-session id on `/api/checks` machines[] as the binding hint — dsh-remote's `resolveRequestBinding` binds a hinted session inside the mirror to that machine's pool — and serves the vendored `@xterm/xterm 5.5.0` + fit/search addons from the whitelisted `/assets/`; fresh sessions `cd` into the machine's `remotePath` = the remote project root; machines without a live remote-project session are disabled with guidance, same precondition as the check buttons; pooled instances keep scrollback across tab/task/reload switches; browser-verified end-to-end on 2026-10-31 against node1 (resume a remote-project session → machine tab → PTY round-trip, auto-cd, snippets, search, font zoom, reopen, pooled reattach — two paint-lifecycle bugs found and fixed in that run, see CHANGELOG Fixed "Terminal sub-tab paint lifecycle"); `tests/terminal.test.mjs` pins the static contracts) and a header button re-opens it pinned on session switches. The Overview carries the local environment button plus one block per machine that has a remote project; a remote check run (`/api/checks/run?machineId=`) borrows a live session of that machine's remote project through `sessionInMirror` and parses the output into columned rows (`checks.js` parsers; `$ROOT` abbreviates the workspace-scope prefix, bjobs column layout comes from the header line). All APIs are served via `ctx.webServer.register` under `/harnessams`; failing checks offer a one-click agent diagnosis prompt. Remote connectivity is delegated entirely to dsh-remote (2026-10-26 rework removed nodes.yaml and the BatchMode ssh channel): a **remote project** is a DSH workspace inside a dsh-remote mirror (`src/server/remote.js` walks up to the nearest `.dsh-remote-meta.json`; one per machine is the recommended setup, created in one click from tier 1 by registering the machine's EXISTING mirror — mirrors are never created here: pick the remote workspace in dsh-remote first, machines without a mirror get an actionable error; the never-working ensure-mirror POST was removed 2026-10-28); checks run through the `rw_exec` tool shell with a real live session as the agent context (its cwd in the mirror binds the machine; the global active machine is never switched; coupling points for the 0.8.66 pin (upgraded 0.8.51→0.8.54 on 2026-10-28 and 0.8.54→0.8.66 on 2026-10-31, exact-pinned in the web profile) live in `src/server/checks.js`'s block comment); remote file browsing/editing is deliberately NOT duplicated — dsh-remote's own tools and web surface do it.
- dsh-remote probe gotchas (verified 2026-10-25/26/27): `tools.execute` REQUIRES `callId` + `AbortSignal` (without a signal the pipeline crashes on `signal.aborted`); `rw_machines` returns a text listing, not JSON (workspace rides on the auth line under each header line); `/dsh-remote/*` HTTP routes sit behind the DSH web auth gate, so same-origin calls forward the incoming request's cookie/authorization headers; a fabricated `{session:{header:{cwd}}}` agent does not survive the tool pipeline (session validated against the live store) — borrow a real session from the host `sessions` service (`sessionInMirror` in `src/server/machines.js`) and pass it to rw_exec as `{id, session}` (rw_exec derives the background-job owner from `exec.agent.id`; an id-less wrapper fails the call before the command runs); call rw_exec with `promoteOnTimeout:false` and an AbortSignal ~30 s above `timeoutMs`, because a borrowed agent has no job controller and a promoted command would be stranded on the remote.
- The client half `src/client.js` is a single-file classic script registered on `window.__ModuleLoader__` (React via the loader's synchronous `require`) — combo-loaded classic scripts cannot `import` sibling modules, so everything browser-side lives in that one file. Keep it that way (no build chain); the `dsh.client` declaration in `package.json` (`inject` + `platform: web`) and `exports["./client"]` must match the loader contract. Wrap every console section in the error boundary so one failure never blanks the rest.
- Client copy is locale-owned (verified against the installed DSH 0.2.1-rc.2, 2026-10-25): all UI strings live in the `L = { zh, en }` dictionary with stable keys and `{param}` interpolation; `wireLocale(ctx)` (called from `apply()`, which requires `exports.inject = ['slots', 'locale']`) registers the dictionary into the DSH locale service (`locale.register`/`locale.bind` — the language follows the client's Language setting) and falls back to the browser language, then English, when the service is absent. zh and en must keep identical key sets; a missing key renders the English text, never the raw key. `exports.meta` localization rides the same contract from the host side: `src/locale/en.json` + `zh.json` carry `{ "meta": { "title", "description" } }` (DSH `readPluginMeta` reads `<pkg>/locale/en.json` through the `exports` map; package.json `name`/`description` stay the en fallback). Do not translate server strings or the diagnosis prompt.
- Safety by default: destructive operations move paths to the trash folder; the best point is persisted to `bestPoints.json` first.
- Custom web routes are not token-gated by the DSH web server: serve only management UI and static reports on them; never expose credentials or remote-execution surfaces without adding an auth layer.
- Workspace convention (runtime, outside any repo — `LocalDesignExample/` being the checked-in exception): a `harnessams.json` at the workspace root provides fixed paths (`ngspice_cmd`, `pdk_lib`, `trash_dir`); relative values resolve against the config file's directory; the plugin locates it by walking upward from the package and from cwd (bare form, or inside `harnessams-workspace/`).
- Repo layout: console plugin package in `src/` (host-half entry `src/index.js` assembling `src/server/` modules, browser half `src/client.js`, plain JS, no build chain; the package also ships `src/assets/` and `src/scripts/` — `PUBLISH.md` holds the must-contain / must-not-contain tarball checks), aggregate bundle in `install_suite/`, starter unit tests in `tests/` (bare `node --test` from the repo root; a directory argument fails on Node 24).
- `src/assets/` holds the **master** `plotly.min.js` for the whole HarnessAMSproject tree (plus its THIRD_PARTY_NOTICES). Never add a second copy anywhere under the project; it ships inside the `dsh-harnessams` tarball and is served in-app at `/harnessams/assets/plotly.min.js`. Report generators do not reference it directly — they seed the workspace-level copy `<workspace_root>/assets/plotly.min.js` from it (discovered by walking up from their own location, via the workspace `plotly_asset` config field, or from a sibling `dsh-harnessams` install under `node_modules/`) and embed a workspace-relative `src`; the CDN is the last-resort fallback. Decision record: `docs/decisions.md` (D-001).
- `LocalDesignExample/` rules: vendored binaries/models stay byte-exact (`.gitattributes` disables line-ending conversion for them); `tools/` holds verbatim copies of the SmartAnaSim pipeline scripts, mirroring the plugin's `common/` + `ngspice/` layout (the plugin keeps `scripts/{common,ngspice,spectre,snp}` and every filename carries its family prefix) — re-sync them whenever the plugin's `scripts/` change; `harnessams.json` there must keep relative paths (portability across clone locations); `demo1/` and `demo2/` are placeholders until the demo milestones land, and any run outputs under them are gitignored, never committed.
- Script-sync check (`src/server/checks.js`): it walks the configured local `sim_scripts_dir` recursively (relative POSIX keys, ≤50 `.py`, skips `__pycache__`) and compares against the remote scripts root — `remote_scripts_dir` when the workspace `harnessams.json` sets it (a REMOTE absolute path; never resolve it against a local base), else the remote workspace root. The remote command uses `md5sum` plus a bounded `find`; keep it in sync with the pipeline's nested layout.
- sky130 closure fact: `combined_models/` alone is NOT a working copy — `corners/*.spice` reference `cells/` models through two levels of relative includes, so the minimal closure is combined_models plus those cells files; copying only combined_models fails with `Could not find include file`.
- Self-contained HTML pages (generated reports) have no bundler safety net: one JavaScript syntax error silently blanks the whole page. Keep the per-section try/catch isolation and test-render after edits. The client half has the same discipline via error boundaries; after editing `client.js`, run `node --check src/client.js` and reload a dev-mount page before considering the edit done.
- Commits require an explicit user request or authorization.
